R4U2 component package contract
================================

R4U2 is the current R4OS update package format. It separates the target R4OS
release, the package version and the embedded version of every component.
None of these values is derived from another.

Package structure
-----------------

An R4U2 file contains a fixed binary header, a UTF-8 manifest and concatenated
payloads. Header and manifest bind sizes, payload count, activation class and
checksums. Each payload has a canonical target, type, size, checksum and
offset. Versioned components additionally declare kind, name, embedded
version and activation behavior. Requirements identify a concrete component,
minimum version and installed/active state.

Versioned component kinds are Kernel, R4X, R4L, R4D and R4P. Configuration,
SDK files and fonts do not receive invented component identities. R4UPack reads
R4M0 or kernel metadata and rejects a manifest that disagrees with the
payload, even if package checksums were recomputed.

R4L means an independent Runtime Library. R4SYS, R4DESK, R4DRAW, R4NET,
R4AUDIO and R4DEV are built into the Kernel and cannot be packaged or required
as separate R4L components. A Platform API implementation update is a Kernel
component update whose ABI remains governed by the central Contract.

Package creation since 0.78.38
-----------------------------

R4UPack uses one reusable 64-KB input buffer. It retains at most 32 open
payload handles and their metadata, reads artifact identity by bounded
positional reads, and computes each payload checksum during the first pass.
The second pass streams payloads into an atomic output file and accumulates
the combined payload/package checksums. It checks source length, timestamp
and payload checksum before publishing the completed header and file.
Changed/truncated input or output errors preserve any previous output file.
Header, manifest, concatenation order and checksums remain byte compatible.

The producer supports at most 32 payloads, 32 requirements, 32 MB per payload
and a 32-KB manifest. The shared manifest contract exposes the journal owner's
package capacity; the producer and update consumer read this same value.
Manifest capacity is shared as well. Excess input is rejected before output
replacement. A package containing unversioned payloads still requires at
least one concrete installed/active component requirement.

The former R4UPack data option is explicitly unsupported. It had no target
accepted by the canonical inventory contract: foreign-drive paths are not
inventory targets, and recognized C: paths belong to their specific kinds.
Explicit data and foreign-drive payload requests return UnsupportedDataPayload.
Supported config/font/sdk targets keep their existing semantics; arbitrary
data is not silently reclassified as system configuration.

Three focused owner cases cover streaming, bounded reads, read/write errors
and preservation of an old output after a same-length source change. Small
mixed component/config packages and an 8-MB SDK payload are byte-identical to
the previous generator. On the local Linux host the 8-MB case used 33,476 KB
peak RSS before and 924 KB after; this is one bounded measurement, not a
whole-release benchmark. The Windows target is cross-compiled, without a
Windows runtime test. No guest installation is part of this host-tool check.

Activation
----------

Only a non-running application-only update may activate live. Kernel,
libraries, drivers, protocols and services require restart. A package that
contains Kernel or Runtime-R4L components is a foundation package. Mixed
packages inherit the strictest class.

Release truth
-------------

The generated release manifest lists the exact components of Slim, Full and
Test. The local profile inventory decides whether the complete release has
been reached; installing one successful package must not update the release
version early. The publish process uploads immutable packages first and the
release manifest last.

SYSUPD validates the entire package before side effects, stages changes,
uses a durable journal, verifies installed metadata, updates the component
inventory and completes restart packages only after the next boot proves the
target state. `VERSION.R4S` and `MODULES.JSON` are engine-owned and are not
valid package payloads.
