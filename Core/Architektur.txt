R4OS core architecture
======================

Kernel boundary
---------------

The kernel owns mechanisms that require privilege or must exist before
modules can be loaded: early boot, page tables, physical memory, interrupts,
timers, scheduling, the initial display path and the minimum storage path
needed to mount the system volume.

Hardware-specific and user-facing policy belongs outside the kernel whenever
a safe load boundary exists. Applications, services, diagnostics, drivers
and protocols are independent repositories and R4M0 modules. A loadable
production path must not retain a silent built-in duplicate.

Boot outline
------------

1. Limine enters the x86_64 kernel and supplies boot responses.
2. Architecture, memory, exceptions, interrupts and timers are initialized.
3. Boot storage and filesystems make the system volume available.
4. Configuration, preload modules and driver policy are applied.
5. The module loader resolves platform bridges, libraries, protocols,
   drivers, services and applications.
6. The scheduler starts normal runtime workers and the desktop/session path.

Public boundary
---------------

Programs never import kernel source. They enter through R4XStart and the six
versioned platform groups R4SYS, R4DESK, R4DRAW, R4NET, R4AUDIO and R4DEV.
Independent Runtime-R4Ls expose their own versioned tables. The canonical
layouts are owned by `Repositories/Contract/`; the SDK provides typed
facades without becoming a second ABI truth.

R4OS has no security boundary between trusted modules. Validation and owner
tracking exist for robustness, not isolation.
