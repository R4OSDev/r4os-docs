R4BASIC execution and performance contract
==========================================

Baseline and cause
------------------
R4BASIC 1.0 capped every scheduled VM slice at 26 instructions and returned
a wake time two guest milliseconds in the future. Runnable code was therefore
limited to about 13,000 bytecode instructions per second before interpreter
or graphics cost mattered.

Current slice model
-------------------
- The shared subsystem runtime still invokes exactly one GuestDriver step per
  host cycle and offers an absolute budget of 262,144 instructions.
- The R4BASIC adapter starts with a 256-instruction clock block and adapts
  later blocks toward one millisecond, never below 64 or above 16,384
  instructions. Production supplies one R4SYS monotonic source and stops at
  the first observed boundary at or beyond eight milliseconds. The stable
  fast full-budget test uses 18 clock reads; the gate caps every step at 20.
- Runnable code returns progress with no artificial wake deadline. Successive
  active cycles continue directly, while an explicit cooperative scheduler
  yield is requested at most once per eight host milliseconds. At 1 kHz this
  changes the former projected 9,034 yields/s into a fixed ceiling of 125/s.
- Console INPUT, bare RANDOMIZE, indefinite SLEEP and foreground audio return
  an event-only wait. Positive SLEEP and TIMER retain their exact one-shot
  guest deadline; foreground audio is woken by source-frame transport
  feedback. Pause and static status windows use the existing
  lost-wakeup-safe R4DESK activity sequence; only the unsupported-facade
  fallback and anomalous zero-operation progress retain a one-tick sleep.
- Host input and lifecycle events are still drained before exactly one guest
  step. One outer host tick is read per cycle; GuestClock is not synchronized
  twice with the same value. Pause time never advances guest time.

The only remaining direct R4BASIC `taskYield` site is the compile-progress
view after a bounded lexer/binder update plus Close polling. The production VM
loop owns its bounded yield cadence in `r4os.subsystem_runtime`; idle guest
progress is counted separately as `zero_progress_waits`.

Lossless input model
--------------------
R4BASIC 1.2.13 / VM contract 1.11.0 declares the input shape it actually
consumes. The SDK translates each printable raw key directly into one text
event, leaves Enter and Backspace as key events, and filters pointer events
before `Viewport.mapClientPoint`. The generic SDK default remains compatible
with hosts that require separate key and text events plus mapped pointers.

Every raw GUI event receives one monotone host sequence and retains its raw
tick. Derived events preserve both values; a queued BASIC byte keeps them
until `INKEY$`, `INPUT`, `LINE INPUT`, `SLEEP`, or RANDOMIZE consumes it.
The VM distinguishes unfocused input, invalid codepoints, unsupported keys or
events, a full 4,096-byte queue, and allocation failure. A rejected delivery
returns `HostPollResult.ignored`: it is counted but cannot wake an event-only
guest or masquerade as accepted work. Input accepted while paused remains in
sequence and is consumed only after resume.

The first-frame snapshot publishes `R4BASIC input` with raw, translated,
filtered, accepted, control, dropped and consumed counts, pending-text and
mouse work, queue fill/high water, per-reason drops, WindowInfo calls and
viewport calculations. `R4BASIC input-correlation` preserves the latest raw,
delivered, accepted, dropped and consumed sequence/tick pairs and associates
the latest consumed event with the first later published frame. These are
passive counters; the hot input path emits no per-event log.

Display and backlog model
-------------------------
VM initialization no longer allocates, clears, rasterizes and publishes an
empty 640x400 SCREEN 0 before the first BASIC instruction. Text output or an
explicit SCREEN operation prepares the real surface after guest execution. A
display-silent running or waiting guest receives a delayed fallback surface;
an immediately terminating guest receives none. Reset remains eager because
the old presenter must never retain a freed surface.

The 33-ms guest cadence now records deferred checks, missed deadlines and
maximum backlog. Each synchronous present records due/start/end age and cost,
and distinguishes published, unchanged, hidden, dropped and failed outcomes.
Full and damage work remains separately visible in the shared presenter.
Up to eight separated text, graphics and presenter regions now survive the
entire producer path. R4DRAW-v5 stores damage as an immutable append-only
generation over the previous committed frame, so a small update no longer
deep-clones the full command/resource payload. The Desktop appends a direct
successor to its cache and invalidates only those client regions; a missing
generation or bounded chain compaction still has a full-frame fallback.

Indexed8 surfaces cross the ABI as a fixed palette plus bounded indexed source
tiles. Integer and fractional viewports therefore avoid the former XRGB32
producer expansion; fractional sampling advances quotient and remainder
instead of dividing for every destination pixel. XRGB32 remains the explicit
compatibility path.

Linear raster operations
------------------------
R4BASIC 1.2.13 / VM contract 1.11.0 keeps the established QBasic pixels and
packed image formats while moving raster work to rows, spans and one local
damage-region list per changed operation. Up to eight separated regions are
retained; touching rectangles merge and overflow uses the smallest area
growth instead of immediately spanning every gap. Text rasterization compares
cached glyph rows and emits one changed span per complete raster scanline; clipped
Bresenham lines carry one incremental pixel index; filled boxes and CLS use
solid spans; PUT decodes into a known destination row. A changed statement
therefore advances the content revision once rather than once per pixel.

PAINT uses scanline flood-fill seeds. A blank 320 by 200 SCREEN 1 now needs
exactly 200 spans, 200 queue pushes and 200 pops for 64,000 filled pixels,
instead of 254,961 neighbor entries. Its queue peak is one in that case.
A same-mode SCREEN keeps its 62.5-, 218.75- or 250-KB allocation and still
clears every byte as QBasic requires. A full ellipse is rejected before its
point trigonometry only when an expanded-screen proof shows that its current
polygon cannot touch a raster pixel; the legal radius-1,000,000 probe records
16,384 requested and 16,384 skipped segments with no pixel or damage work.

Numeric arrays already use native compact storage on the x86_64 target. GET
now packs directly into the required raw prefix and PUT reads the prefix named
by the four-byte header. The oversized-array fixture preserves its distant
LONG element while each 8 by 8 SCREEN 9 transfer exposes only 36 bytes, with
no whole-array allocation or element encode/decode pass.

The host acceptance fixes complete text and mixed-primitive raster hashes plus
the packed-image hash. It also fixes 256,000 logical pixels / 400 full raster
rows with one damage commit, 45 spans for a 58 by 45 filled box, the PAINT
queue bounds, same-address SCREEN reuse and the GET/PUT prefix counts. The
checksum-bound gorilla.bas full-round raster, palette and audio golden values
remain unchanged. The first-frame report publishes the same allocation,
pixel, span, damage, paint, circle and image-prefix counters as
`R4BASIC raster`. `R4BASIC damage` separates commits, retained regions,
ordinary merges, overflow merges and forced full commits. `R4BASIC presenter`
reports full/delta/compaction frames, regions, Indexed8 blocks and resource
bytes, XRGB fallback frames, raster blocks and sampled pixels.

Historical TIMER polling
------------------------
Removing global pacing must not turn CalcDelay/Rest-style TIMER loops into an
unbounded host-speed benchmark. The VM therefore permits one TIMER read per
guest millisecond in scheduled mode. An earlier repeated poll returns a
cooperative wait until that guest deadline; all non-TIMER bytecode continues
at the measured slice rate. Direct deterministic VM tests may leave this
adapter behavior disabled.

Demand-driven audio model
-------------------------
R4BASIC 1.2.13 no longer couples BASIC progress to a calculated guest-time
audio deadline. Every PLAY/BEEP appends a cumulative source-frame fence. MF
and BEEP retry their bytecode instruction only after runtime feedback has
classified every frame up to that fence as accepted by AudioService,
deliberately suppressed silence, or an explicit discard. MB still lets the
next BASIC instruction execute immediately; when a fast END follows in the
same slice, the adapter keeps only the host transport alive until its pending
frame fence is resolved. The VM never equates service acceptance with hardware
playback. R4AUDIO/AUDSVC currently exposes no per-stream hardware cursor, so
the report fixes that state as `playback=unavailable`.

The generic runtime opens no stream for an empty or all-zero renderer. Pause
and mute close an active stream once and submit no replacement zeros. Eight
independent silent R4BASIC VMs therefore use zero of the eight AudioService
sessions; an active path remains isolated rather than sharing a R4BASIC
hardware mixer. Passive counters separate active/silent/paused/muted cycles
and bytes, service opens/writes/closes, Busy/resync, and scheduled, accepted,
suppressed, discarded, resolved and unresolved source frames.

R4BASIC retains four 40-ms source quanta for the 160-ms HDA start reserve,
but Open, prefill, steady write and deferred Close are serialized to at most
one synchronous service operation per host cycle. Pending video is published
first. Successful prefill and resync writes continue through fresh cycles;
Busy retains the exact PCM and retries after 10 ms rather than advancing a
whole 40-ms quantum. The R4BASIC facade bounds an individual service call to
25 ms and keeps the existing three open retries 50 ms apart. A late resync
reports discarded queue bytes instead of silently advancing unrendered notes.

PLAY appends transactionally into the retained event list after one bounded
capacity reservation. Invalid input rolls the logical length back, so music
settings and queued events stay atomic without a temporary event list and
second persistent copy. An 85-entry compile-time phase-step table replaces
one floating-point power per note. The 4,096-note component case proves one
capacity growth, 4,096 direct appends and 4,096 table lookups.

graphics, text and host groups and additionally expose cancel-flag/callback,

Dispatch and bytecode locality
------------------------------
R4BASIC 1.2.6 stores the hot opcode and two operands in one 12-byte
instruction stream. The exact 16-byte source span plus statement start and
successor occupy a parallel 24-byte cold stream. Both have identical lengths
and preserve O(1) diagnostics, ON ERROR, RESUME and RESUME NEXT, but the
normal dispatch fetches only one third of the former 36-byte record. At the
262,144-instruction limit the hot stream is 3 MB and the cold stream 6 MB; the
196,609-instruction dense maximum-source fixture reports 2,359,308 hot and
4,718,616 cold bytes instead of fetching all 6.750 MB as one stream.

Cold metadata is read only when control enters a different BASIC statement
or an error needs its exact span. The injected cancellation callback is read
once per bounded adaptive VM chunk; the independently set Close flag still
wins between individual instructions. Opcode-group accounting uses a complete
compact table. Text rasterization is checked after text bytecode and at real
display boundaries rather than after numeric and control bytecode.

The compiler records comparison operand promotion in the existing operand.
INTEGER and LONG pairs compare exactly as integers; floating and mixed
floating comparisons retain the previous binary64 path. ResolvedCell is a
separate internal type, so global/local and flattened ByRef targets are not
resolved again by load/store. A same-type store transfers the owned stack
value; conversion and QBasic rounding remain active only when the bound target
really differs.

String ownership, built-ins and procedure frames
------------------------------------------------
R4BASIC 1.2.9 retains bytecode contract 1.5.0 and advances the VM contract to
1.8.0 for the event-driven host-cycle rules. Loading a
string variable still creates the distinct owner required by QBasic assignment
semantics, but a same-type store now moves that owner instead of cloning it a
second time. A simple `B$ = A$` therefore performs exactly one full-string
clone and leaves source and destination independently owned.

The compiler emits scalar references for simple string lvalues used as
read-only built-in arguments. Numeric arguments retain their established value
evaluation because copying those fixed-width scalars has no string/heap cost.
The VM presents those Cells as non-owning Value views to LEN, INSTR, UCASE$,
VAL and the other built-ins; expression results remain owned stack values.
Only owned arguments are destroyed after the call, while every returned string
has independent storage. The compiler and VM count borrowed/owned arguments,
string clones and clone bytes so error and lifetime paths remain observable.

Procedure-local storage is retained by active recursion depth rather than
allocated for every call. A generation per depth lazily materializes only
parameters, returns and locals actually reached by bytecode. An intrusive list
tracks those initialized slots for exact reverse cleanup on RETURN, runtime
error, reset and VM destruction. Recursion uses a separate pool depth, and two
VM instances never share capacity or Cells. Calls, pool growth/reuse, initialized
Cells and aggregate initializations are reported independently.

Numeric PRINT and STR$ format into a bounded 128-byte stack buffer; STR$ then
allocates only its final QBasic result. VAL parses ordinary E/e or exponent-free
text directly. D/d text up to 128 bytes is normalized on the stack, while a
longer value grows one retained VM scratch buffer and reuses it. The first-frame
`R4BASIC ownership` record publishes all these counters, and the Distribution
marker gate validates their pool, initialization, format and scratch
invariants.

Array and VM storage
--------------------
R4BASIC 1.2.8 no longer represents every numeric array element with the
56-byte tagged Cell. INTEGER, LONG, SINGLE and DOUBLE arrays own contiguous
2-, 4-, 4- and 8-byte slices. A 1,024-element INTEGER array therefore uses
2,048 instead of 57,344 payload bytes; the corresponding LONG/SINGLE and
DOUBLE payloads are 4,096 and 8,192 bytes. References carry a typed scalar
pointer or a Cell pointer, so element ByRef and numeric GET/PUT raw-byte views
retain their existing semantics. Strings and records remain on the safe
generic Cell representation.

The representative component workload dimensions four 1,024-element numeric
arrays and expands the INTEGER array to 2,048 elements. Its final and maximum
aggregate live payload are both 20,480 bytes; the conservative atomic resize
peak, including old/new dimension records, is 22,560 bytes. Compact OOM leaves
the four-element LONG array and its value intact. A generic 262,144-element
wide-record DIM is rejected before payload allocation. The VM enforces 128 MiB
aggregate logical live payload and 192 MiB for an atomic resize transition;
the element-count limit remains 16,777,216 per array.

Sequential files now use a 256-byte direct file-number index plus dynamically
owned slots for open files. Lookup remains O(1), CLOSE publishes no partial
slot change on a failed write, and the static VM object is 8,568 bytes instead
of 30,440. The first-frame `R4BASIC storage` record exposes compact/generic
resize work, aggregate live/peak bytes, both limits, VM static size, index
size, capacity growth and maximum concurrently open files.

First-frame launch timeline
---------------------------
Explorer attaches diagnostic R4SUBSYS1 records only to `r4os.basic` starts.
They carry a 16-digit launch ID, GUI/headless mode and the elapsed probe,
resolution and Desktop-host-request boundaries. Desktop completes the third
boundary before spawning the host. If the optional records do not fit the
127-byte argument limit, Explorer preserves the established uninstrumented
launch instead of rejecting a valid guest path.

The Kernel recognizes these records only for passive observability. It writes
bounded serial records for admission, completed R4M0 loading and R4XStart with
the same ID. The loader record contains actual range-read and filesystem-gate
deltas plus section, import and relocation counts. R4BASIC writes one bounded
`C:\TEMP\R4BASIC.LAST` snapshot at the first guest-driven published frame;
source I/O, compilation, VM/host initialization, first executed slice, lazy
audio open and first frame all use the common monotonic nanosecond clock. The
legacy `initial_frame_ns` field must remain zero, proving that no
pre-instruction full frame was emitted.

The Test profile adds a separate headless mode without replacing the two
synthetic subsystem lifecycle instances. It resolves `r4os.basic` explicitly,
loads `C:\TEMP\GORILLA.BAS`, verifies the canonical 29,434-byte SHA-256-bound
source, compiles it in the productive R4BASIC GUI artifact and exits only
after a guest-driven frame was published. `C:\TEMP\R4BASIC.BASELINE` records
the complete timeline and real-work counters; the serial marker gate binds
that report to the Kernel records by launch ID and rejects missing, reordered
or zero-work phases.

Compiler scalability and launch responsiveness
----------------------------------------------
R4BASIC 1.2.6 classifies its 103 supported and 84 reserved keywords through a
compile-time hash table whose current worst lookup is eight probes. Separate
case-insensitive open-addressing indices own globals, per-procedure locals,
procedures, record types, per-record fields and scoped labels. Branch and DATA
fixups resolve through the label index instead of rescanning every label.
Array, record and ByRef statement paths reuse the binding already obtained for
statement disambiguation. Original source spans and casing remain the sole
diagnostic and bytecode source positions.

The compile report records lookup, insertion, probe, maximum-probe, rebuild,
fixup and reused-binding counts. Host stress coverage binds 128 record types,
512 arrays, 256 procedures and 1,024 fixups twice with identical bytecode and
at most 64 observed name probes. A separate test accepts a complete 256 KiB
source and cancels the same workload during lexing without leaked ownership.

Compiler-state bounds
---------------------
The compiler first performs an allocation-free lexical census and allocates
exactly the token count later emitted. At the 256-KiB source limit the dense
case contains 262,145 20-byte tokens, or 5,242,900 bytes, instead of an
unconditional maximum buffer. A token-derived demand pass precisely reserves
the twelve long-lived builder lists, including parallel hot and cold
instruction storage. Numeric and string literals use a
content index; integer values, exact SINGLE/DOUBLE bits and string bytes are
the identity, so repeated constants retain one program entry. Decimal and
D/d-exponent parsing does not allocate a temporary heap copy.

Production transfers the loaded mutable source allocation through
compileOwnedObserved and the Program keeps that same storage. The API consumes
the allocation on success, diagnostics, cancellation and allocation failure;
the borrowed entry points remain available and copy. Compiler diagnostics
retain at most the first 20 records while exposing total and truncation
counts. Frontend and bytecode compilation reject expression nesting beyond a
deterministic 128-level limit.

The host acceptance pairs sparse and dense valid 256-KiB sources. Sparse
source must remain below a 512-KiB requested peak. For 65,536 repetitions of
`A=1:` the PageAllocator measurement is 12,605,977 peak bytes, 7,340,137
retained program bytes, 7,095,028 initial-list bytes, 17 allocations, four
reallocations and zero copied bytes; all 65,536 integer literals reuse one
constant. Stable acceptance ceilings are 20 MB peak, 8 MB retained program,
128 allocations and 8 MB copied. The productive GORILLA marker additionally
publishes requested token/list/peak/program figures and actual VM allocator
allocation, free, active, peak, reserve and commit snapshots around compile.

The productive GUI creates its program window before compilation. Lexing
reports after at most 2 KiB and binding/fixup work after at most 256 entries;
each callback polls Close, Escape and the R4OS lifecycle, publishes a bounded
phase/percentage view and yields. The successful VM rebinds the same host
window to its guest surface. The headless marker gate requires a visible
compile frame, progress updates and bounded compiler counters before accepting
the later canonical guest frame.

performed no write. Active playback opens lazily after the first non-silent
quantum, performs at most one open/write/close service operation per host
cycle, retries Busy after 10 ms without losing the queued quantum and closes
idempotently. Foreground PLAY/BEEP waits for accepted, suppressed or discarded
source frames instead of guest time; background audio survives an immediate
END until that transport progress is resolved. The direct PLAY builder
appended 4,096 notes after one bounded reservation and used the fixed phase-step
table without a temporary sequence or runtime power calculation. The one warm
`perfdiag.clock.calls-10000.v1` completion benchmark produced
1,804/1,022/790/790/787 ns per call, mean 1,038 ns. Against the directly
comparable 0.69.63 mean of 796 ns this is 242 ns or 30.40 percent slower. The
change is accepted as variation of the migrated host environment rather than
attributed to the audio path. The result is stored under run ID
`r4os-0.69.64-perfdiag-clock-warm-20260826t083506096z-27b20e74`.

The 0.69.65 completion gate made BAS dispatch metadata-first and the source
load single-owner. Explorer and Desktop resolved the installed `r4os.basic`
association with one file-info call and zero content reads; R4BASIC then
allocated the exact 29,434-byte GORILLA source buffer, filled it with one
range read and transferred that same allocation into the compiler. Owner
tests covered valid sources immediately below, at and above 128 KiB and at
the 256-KiB limit; a 256-KiB-plus-one source was rejected before any content
read. Standard and SMP guests both published the exact zero-read upstream and
one-read R4BASIC markers. The one warm
`perfdiag.clock.calls-10000.v1` completion benchmark produced
1,345/839/841/839/840 ns per call, mean 940 ns. Against the directly
comparable 0.69.64 mean of 1,038 ns this is 98 ns or 9.44 percent faster; the
run-to-run change is treated as migrated-host variation rather than attributed
to BAS source loading. The result is stored under run ID
`r4os-0.69.65-perfdiag-clock-warm-20260826t090901623z-1a8d8ff0`.

The 0.69.66 completion gate replaced whole-file sequential BASIC I/O with one
bounded asynchronous request at a time. The exact 4-MiB INPUT owner test used
64 data refills plus one EOF read instead of 1,025 synchronous 4-KiB reads;
the maximum request was 64 KiB and the rolling input buffer stayed within
128 KiB. The same test streamed the exact 4-MiB OUTPUT through 1,024 forced
4-KiB partial completions, with requests bounded to 64 KiB and the final data
drained by END. Separate owner cases cover a one-byte file, CR/LF boundaries,
APPEND and CLOSE, positive partial progress followed by failure and RESUME
without duplicated bytes, and reset/deinitialization while a request must be
quiesced. Pending storage waits yield the VM for 1 ms, so guest input, video,
audio and close handling continue between polls. The four-entry raw-to-typed
path cache normalizes a repeated path once, and the new marker exposes calls,
bytes, polls, completions, path resolutions, request bounds, compaction and
actual rolling-buffer peaks. Standard and SMP headless guests parsed that
marker successfully; all counters were correctly zero for the canonical
GORILLA program because it performs no sequential file I/O.

The SDK typed-path constructors now initialize only the canonical bytes and
terminating NUL rather than clearing the entire 1-KiB result. Their two
160-entry rollback tables use 16-bit indices and therefore occupy 640 instead
of 2,560 bytes; Zig and C owner tests enforce both properties. The remaining
global-storage finding was already removed structurally by the per-volume,
per-controller and asynchronous block/filesystem work in 0.69.35 through
0.69.40, so 0.69.66 required no new kernel artifact. The one warm
`perfdiag.clock.calls-10000.v1` completion benchmark produced
838/830/834/831/833 ns per call, mean 833 ns. Against the directly comparable
0.69.65 mean of 940 ns this is 107 ns or 11.38 percent faster; the run-to-run
change is treated as migrated-host variation rather than attributed to BASIC
file I/O. The result is stored under run ID
`r4os-0.69.66-perfdiag-clock-warm-20260826t101157604z-96e26546`.

Outstanding visual acceptance
-----------------------------
The automated headless gate now proves productive QEMU window presentation to
the first canonical GORILLA frame. It does not replace the remaining manual
interaction acceptance: open the unchanged source through Explorer, check at
least 20 presented frames per second plus keyboard/Close latency below 100 ms,
then repeat the same hardware-independent guest timing on the Lenovo laptop.
