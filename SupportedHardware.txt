R4OS supported hardware
=======================

Primary target
--------------

The primary and continuously reproducible target is x86_64 QEMU using the
profiles from `Repositories/Distribution/QEMU/`. The standard module build
targets AVX2-class processors. The kernel itself is built without SIMD.

Current hardware classes
------------------------

- Boot/display: Limine and a linear framebuffer. DISPBLIT.R4D accelerates the
  bounded XRGB32 CPU copy through the canonical present contract; no native
  display-controller modeset, pageflip or GPU command backend is claimed yet.
- Storage: AHCI, NVMe, ATA PIO and USB mass storage paths exist. DOS/MBR and
  GPT partition discovery is supported on 512-byte logical sectors; GPT
  recognizes EFI System and Microsoft Basic Data partitions and can recover
  through the backup table. NTFS is the system-volume format; FAT32 remains
  available for boot and additional media.
- Input: PS/2 and USB HID keyboard/mouse paths.
- Timers: periodic PIT is the boot and degraded fallback. A free-running HPET
  supplies the modern logical tick; HPET legacy comparator 0 or a calibrated
  LAPIC supplies periodic active delivery and one-shot idle deadlines when the
  required ACPI/IOAPIC capabilities validate.
- CPU: x86_64 ACPI/LAPIC SMP with one BSP and up to 31 APs. INIT/SIPI startup,
  per-CPU architectural state and partial-AP failure fallback are covered on
  QEMU; one-CPU operation remains fully supported. CPU hotplug is not claimed.
- Network: RTL8139, RTL8168/RTL8111 and modern virtio-net drivers.
- Audio: AC97 and class-based High Definition Audio (HDA) output drivers
  plus MIDI, OPL3 and SID modules.
- USB: xHCI host controller and HID/mass-storage protocols.

HDA 0.3.15 / Kernel 0.1.104 add separate HDA controller instances and a
physical output catalog. A short SMP4 QEMU test selected both of two HDA
controllers and sent PCM through AUDSVC, with eight backend writes and zero
new errors per route. HDMI stereo PCM setup is implemented for an explicitly
supported receiver with valid ELD. NVIDIA additionally needs the display
engine's HDMI-audio enable and presence/ELD handoff; the existing linear
framebuffer does not establish that capability. On OssiPC the updated driver
enumerated four NVIDIA 10DE:228E HDMI pins, all with absent receivers; the
10DE:2504 graphics function has no native display driver. HDMI activation is
still unproven and its display handoff remains open. Four analog outputs on
the AMD controller were also enumerated. See Drivers/HdaStreamContract.txt.

OssiPC was updated and rebooted into release 0.78.18 on 2026-09-08, with
Kernel 0.1.104, HDA 0.3.16, AUDSVC 0.1.9 and R4DESK 0.1.39. SYSUPD confirms
the three-component audio package installed; the running service exposes all
eight outputs to the new Desktop selection. HDMI receivers remain absent.
The HDA idle correction passes focused SMP4 checks. Its isolated OssiPC
comparison was not completed before the hardware became unavailable. Per
the user instruction of 2026-09-08, the remaining 0.78.X roadmap tests used
local QEMU with four vCPUs while OssiPC and Lenovo were unavailable. Previously captured
post-update logs show LPIB fallback with no position recovery or hardware
error, but do not establish an isolated hardware comparison or HDMI playback.
See Drivers/HdaStreamContract.txt for evidence limits.

OssiPC is available again for targeted 0.79.X work as of 2026-09-09 at
192.168.178.105. A read-only SSH check confirmed release 0.78.76 with active
and installed Kernel 0.1.132, 16 logical CPUs and 24731 MB physical RAM.
RTL8168 reports link up and a bound DHCP lease; all three host pings received
replies. SERVMAN reports 14 running/starting services, zero failed services
and SSHD running on port 22. The changed SSH host key was saved with explicit
user approval. This establishes remote access, not a new audio or USB
acceptance. Lenovo availability was not checked. The diagnostic summary is
under Temp/ossipc-connectivity-20260909.txt in the coordinating workspace.

The same day's HDMI diagnosis identifies the boot monitor as HISENSE
(manufacturer HEC, valid base-EDID checksum). The user confirms a Hisense
65U8QF directly connected to the NVIDIA HDMI port. Its EDID advertises one
extension, but Limine exposes only the 128-byte base block. All four NVIDIA
HDA pins still report absent receivers. Complete connector EDID acquisition
and the NVIDIA display-to-HDA audio handoff remain unimplemented; see
Drivers/HdaStreamContract.txt and Temp/ossipc-hdmi-07901/ for the evidence.

The current xHCI backend initializes only the first controller found in PCI
order. Additional xHCI controllers remain uninitialized; attached keyboards
and storage on those controllers are unavailable. The inventory currently
repeats the global xHCI host status for every xHCI PCI function, so an
"active" inventory record does not prove that a particular controller was
initialized. This limitation also applies to Recovery 0.1.20.

An OssiPC SSH diagnosis on 2026-09-07 found three AMD 1022:149C controllers
at 06:00.1, 06:00.3 and 0B:00.3. The complete boot log records only 06:00.1
starting; initially USBHID and HIDREPORT are loaded without enumerated USB
devices. Moving the keyboard beside the USB stick did not help. Moving it
to the lowest of the three rear USB pairs made it work: the user confirmed
input, SSH reported 04F3:152E as USBHID/bound-input, and the boot log recorded
successful port events. The USB stick in the upper pair still needed a
supported port. This verifies a port workaround, not support for the
remaining controllers. Evidence is under Temp/ossipc-usb-20260907/ in the
coordinating workspace.

Recovery 0.1.20 resolves its physical boot source once during startup and
hides USB storage when the source is unknown. After moving a previously
unrecognized boot stick to a supported port, restart Recovery so it can
identify and mount the installation source.

The normal OssiPC installation was diagnosed over SSH with R4OS 0.78.14 /
Kernel 0.1.102 on 2026-09-07. Its two large NTFS volumes D: and F: each expose
about 976 million clusters. Repeated free-space queries took 6.8-7.2 seconds
per volume while directory enumeration and entry metadata took 1-8 ms.
Explorer invoked that full bitmap scan on startup and every folder change.
This identifies a filesystem scaling issue; no storage completion timeout
occurred in the measured calls. The fix and count lifetime are documented in
FileSystem/DateisystemUndStorage.txt. On 2026-09-08 the user-approved R4U update
and restart activated Kernel 0.1.103; SYSUPD confirmed the batch as installed.
The same read-only probe measured initial D:/F: counts at 2.100/2.370 seconds
and subsequent counts at 94/93 microseconds with no device reads. Both free
cluster counts matched the pre-update values. The initial scan after a restart
remains visible; these timings do not measure complete GUI frames.

Recovery input (0.76.5)
----------------------

Recovery uses the same PS/2 and USB HID keyboard paths and R4OS keyboard
layouts. Its HID admission excludes mice, including later topology changes;
the normal R4OS defaults remain unchanged. Hiding USB storage during a local
Recovery boot does not hide USB keyboards or disable their host controller.
The automated input acceptance covers QEMU PS/2 and USB keyboard models,
USB/local boots and BIOS/UEFI with four CPUs. USB-only cases disable i8042.
This does not establish compatibility with every physical USB keyboard.

Real hardware
-------------

R4OS has been booted from USB on real hardware, including a Lenovo IdeaPad
L340-15API with a Realtek RTL8168-family adapter. This is evidence for that
specific path, not a general compatibility promise. Firmware, ACPI, PCI
routing, storage controllers and display setup vary widely between machines.
Always keep a recoverable copy of important media.

The same Lenovo system has also completed an internal-drive boot through
Limine and AHCI.R4D 0.2.1 from a KINGSTON SUV400S37120G SATA SSD. Its NTFS
system partition mounted as `C:` while the separate Intel NVMe remained
available as an additional GPT device. The live acceptance observed two
preload-owned block devices, no built-in storage fallback, a successful
Device Manager storage selftest, RTL8168 DHCP and an SSH session.

The Lenovo audio path is documented in `Drivers/HdaStreamContract.txt` and
`Drivers/HdaHardwareAcceptance07110.txt`. HDA.R4D 0.3.13 enumerated both AMD
functions `1002:15DE` and `1022:15E3`, selected the latter with Realtek
`10EC:0257`, and passed cold/warm starts, internal-speaker playback, volume
and mute. Analog headphones remain untested. HDA support is selected by
PCI class 04/03 and is not limited to Intel controllers.

Images
------

Prepare installation media with the release's `CreateUSB.bat` on Windows
or `sudo sh CreateUSB.sh` on Linux. Both use PowerShell 7 and the original
release ZIP. Besides writing the GPT image, they place the original ZIP in
the Recovery installation cache and size DATA for the destination medium.
A raw copy of `disk.img` alone does not add that ZIP. See
`Deployment/USB-Erstellung.txt` for the supported workflow.

Security warning
----------------

R4OS is not hardened. Network services may use the standard credentials
`r4os` / `rosebud`. Never expose SSH, FTP, RDP or other R4OS service ports to
the public Internet or an untrusted network.
