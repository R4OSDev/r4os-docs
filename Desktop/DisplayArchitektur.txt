R4OS display architecture
=========================

Layers
------

- Boot display: early and fatal output on the Limine framebuffer.
- Display manager: active backend, geometry and presentation.
- Software surfaces: validated XRGB32 pixel storage.
- R4DRAW: public drawing, font, image, surface and frame operations.
- R4DESK: windows, events, desktop state and remote-frame access.
- Desktop R4X: composition, policy and visible user interaction.

Applications draw through R4DRAW into their assigned targets. The desktop
owns window placement, clipping, damage, z-order and final presentation.
Early boot output remains separate and is invalidated when the normal
desktop takes ownership.

Software surfaces use XRGB32. Width, height, pitch, clipping and source/
destination rectangles are validated before pixels are published. Remote
desktop services consume completed frames through R4DESK and return input
through the same contract; they are not a second display owner.

Damage and presentation
-----------------------

The Desktop retains up to eight separated dirty regions. Overlapping regions
are merged; a ninth separated region collapses the generation to its bounded
union, and an explicitly invalidated complete scene remains the full-frame
fallback. It composes each retained region only through scene owners whose
bounds intersect it. Background, wallpaper, grid, desktop items, windows,
taskbar, menus, dialogs and cursor keep their existing z-order; complete
non-intersecting layers and windows are rejected before their paint work,
while desktop-item bounds are checked before icon loading and rendering.

R4DRAW slots 33 through 35 are the canonical present contract. A request
identifies one XRGB32 source generation, its dimensions and stride, up to
eight damage rectangles and an optional input tick. The result reports the
single present generation, exact region and pixel work, backend, fallback,
error, synchronous fence/completion and input-to-present ticks. Capabilities
name both the selected backend and the CPU fallback. Every region is
validated before the first visible write. Unsupported, absent or failed
external backends therefore copy the complete accepted generation through
the boot framebuffer without partial external/CPU mixing.

The old single-rectangle stride slot 32 and packed-source slot 9 remain
compatibility entries, but both feed the same presenter and DisplayManager.
Only DisplayManager owns productive present counters, fences, backend choice
and fallback; the Surface and compatibility frame lifecycle keep no parallel
statistics.

Hosted application frames
-------------------------

R4DRAW-v5 extends the append-only table at slots 36 through 38. A producer
starts a damage generation with up to eight exact client rectangles. The
kernel retains one immutable full base plus bounded immutable deltas; it no
longer deep-clones the committed command/resource payload for every small
change. A reader can request metadata and bytes for one generation or use the
existing full-frame read as a flattened compatibility view. Owner handles,
generation numbers and retired-reader lifetimes remain validated at every
read boundary. A full generation compacts the chain after at most 31 deltas.

`GuiIndexed8Resource` carries a fixed header, 256 XRGB palette entries and an
at-most-128x128 indexed source tile. The command records destination geometry
separately, so integer and fractional scaling do not require producer-side
XRGB expansion. Desktop appends a direct successor delta to its active cache,
rebases only the new resource offsets and invalidates only the supplied
regions. Missing generations, unsupported tables, invalid payloads and
allocation failure retain the previous complete frame and use a bounded
full-snapshot retry. Rendering rejects non-intersecting commands before
touching their payload and resolves Indexed8 pixels only inside the active
scene paint clip.

Terminal windows use a separate fixed snapshot cache keyed by console
revision, geometry, font, codepage and scroll offset. Cursorblink reads the
cached state and contributes only its small cursor rectangle to the same
regional Desktop/DisplayManager present path.

Backend inventory and first acceleration
----------------------------------------

The reproducible QEMU and current real-hardware path exposes a Limine linear
boot framebuffer. R4OS currently has no owned display-controller BAR,
modesetting contract, scanout buffer allocation, pageflip interrupt or GPU
command queue. The standard QEMU configuration also declares no explicit
GPU device contract. A hardware pageflip/GPU claim would therefore lack an
owned target and a completion source.

DISPBLIT.R4D is consequently the first and only external accelerated
consumer: an owner-bound, resident module that performs synchronous XRGB32
multi-region fast copies with module SIMD, volatile target stores and a final
store fence. It borrows framebuffer, source and region addresses only for the
callback. Its bounded self-test covers two separated regions and unchanged
surroundings before registration. Unload first closes callback admission and
cannot retire the owner while a call is active. The kernel retains the safe
format-aware CPU copy as the complete fallback and does not contain a
driver-specific DISPBLIT special case.

DISPLAYD measures exact region/pixel work, synchronous fence completion and
input-to-present ticks in the guest. The Desktop headless gate additionally
checks small separated damage, culling, zero lost generations, remote shadow
demand and the active/fallback capability pair. The release benchmark remains
the project-wide comparison; it is not interpreted as proof of GPU support.

The remote XRGB32 shadow is a readback product, not part of local display
presentation. R4DESK slot 56 accepts the same bounded region generation, but
keeps a bounding dirty rectangle in the legacy reader metadata. RDPSVC,
RFDIAG and other readers acquire a remote-frame consumer for their actual
lifetime. The first consumer wakes Desktop and causes a complete publish;
after the last release the live shadow and mapped snapshots are discarded.
Local-only frames therefore neither allocate nor copy a second full-screen
image. Frame revision, dirty union and stable map generation retain their
existing meaning while a consumer is active.
