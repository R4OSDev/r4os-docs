R4OS update workflow
====================

This document describes updates of the running R4OS installation. Since
0.76.7, the separate RAM-based Recovery may directly repair offline volumes
through SSH/SFTP/SCP/FTP. Those file operations do not invoke this update
engine, and executables are loaded from the Recovery RAM runtime.

Components
----------

- UPDSVC searches the configured package server, downloads packages and owns
  the single durable update job.
- UPDATE.R4X is the graphical frontend.
- SYSUPD.R4X is the administrative verification, apply, resume and status
  frontend.
- The shared update engine owns package parsing, staging, journal, rollback,
  inventory and post-boot completion.

Search and download never install by themselves. The service validates the
catalog schema, immutable filename, size and SHA-256 before handing a package
to the common engine. All frontends observe the same job and cancellation
state; they do not implement parallel installers.

Install flow
------------

1. Validate package structure, identities, requirements and targets.
2. Verify every payload while writing its private stage on the target volume.
3. Persist a journal and revalidate the staged bytes.
4. Commit live-safe applications or bind restart-required packages into one
   restart batch.
5. On the next boot, recover or finish every pending transaction.
6. Advance the release only after running and installed components match the
   release manifest for the local image profile.

Since 0.78.10, a fresh download hashes confirmed sink bytes during transfer;
a resumed download first hashes only its retained PART prefix. A bad transfer
is discarded before publication. The service then verifies the published
file's size and SHA-256 once before reporting download success. No pathname,
size or timestamp cache substitutes for this final check.

VERIFY and Update All's preflight remain complete, side-effect-free payload
checks. Live STAGE/APPLY combines payload verification with private staging.
Restart STAGE verifies before persisting its package binding; COMMIT plans
from metadata, then verifies each package while staging the entire batch
before the first active replacement. Each payload pass rechecks the exact
header, manifest bytes and file length at its end. Journal binding, checksums,
private-stage ownership, checked replacement and recovery remain authoritative.
For a successful fresh Update All download, post-transfer full payload passes
fall from six to three for live packages and seven to four for restart packages.
Retained-prefix reads and bounded metadata reads are additional work; retries
may add passes. SYSUPD reports actual payload stream attempts and bytes read.

R4M0 strings and ELF section names use the shared 512-byte bounded artifact
reader in all engine phases. UpdateCenter uses additive UPDSVC operations 10
and 11: the complete offer plus its first component, then up to eight further
components per response. Both fit the existing 4096-byte IPC limit. Old
single-row operations remain available. Job and result-generation checks
reject mixed snapshots, including changes to offer state or inventory.
The GUI keeps one asynchronous request outstanding and publishes a completed
private model only after all pages validate. Close releases the outstanding
request without cancelling the service's independent update job. The maximum
64-package/192-component fixture needs 128 calls instead of 256; package
descriptions retain their full 2048-byte capacity.

Interrupted uploads and downloads use explicit temporary ownership and
compare-and-delete cleanup. A foreign file is never removed merely because it
uses the same name.

R4X subsystem handlers below `C:\\R4OS\\SUBSYSTEMS\\<id>\\` are versioned
application components. R4UPack and SYSUPD classify their `.R4X` payloads as
software updates while retaining the canonical `/R4OS/SUBSYSTEMS/...`
component target in MODULES.JSON. A subsystem payload is never treated as
generic data and never installed by direct SFTP replacement. The same narrow
`.R4X` target class is accepted by the durable transaction journal and the
kernel's boot-recovery parser; save data and other subsystem files remain
outside the update target policy.

R4U2 component metadata covers identity, version, kind and target. It does not
carry the profile-owned `MODULE_ROLE`, subsystem ID, guest formats, extensions
or features from `module.R4MF`. SYSUPD therefore preserves those fields for an
existing schema-4 catalog entry but cannot invent them when a subsystem is
added to a manually assembled older image that never contained that entry.
Adding a wholly new subsystem belongs to a matching generated profile/release.
Recovery of a mixed-version image must restore the exact canonical catalog
entry from that image plan; an association alone is not an installation.

A batch without a durable transaction journal can be discarded with
`SYSUPD ABORT-BATCH`. This is limited to the preparatory staged, verifying and
staging states. SYSUPD reconstructs every private stage from the still-bound
packages and deletes it only when length and checksum match; system targets
and retained last-good backups remain untouched. Once a transaction journal
exists, RESUME or RESUME-BATCH is required instead.

Recovery: complete system replacement (0.76.19)
---------------------------------------------

The Recovery menu's Update R4OS uses R:\INSTALL\RELEASE.ZIP or its verified
download replacement. It identifies SYSTEM and BOOT by the installation
manifest and actual GPT identities. It rebuilds SYSTEM at its existing
size, including newly prepared NTFS metadata, and removes all previous
system files and settings. A smaller or larger existing SYSTEM is accepted
when the complete new contents fit. There is no automatic partition resize.

The matching normal kernel and preload files come from that same release.
BOOT files are replaced individually; existing limine.conf bytes, foreign
files, GPT and all partition boundaries/IDs are retained. DATA and RECOVERY
are preserved. The configured R4OS kernel/preload references and installed
BIOS stages must match the supported boot contract before writes begin.

Package contents and both write plans reside in RAM before separate BOOT
and SYSTEM claims. Source identity and BOOT bytes are revalidated under the
claims. Successful completion requires flush/readback, restored mounts and
the new installation manifest. An interrupted write is reported as incomplete
and has no automatic rollback. Recovery remains available for repair in RAM.

Recovery: CURRENT/PREVIOUS replacement (0.76.20)
----------------------------------------------

Update Recovery consumes the independently released package at
R:\INSTALL\RECOVERY.ZIP. It replaces only the selected RECOVERY partition's
CURRENT files; INSTALL, all other partitions and existing limine.conf bytes
are preserved. The complete package and both FAT write plans reside in RAM
before the exclusive claim. The filesystem is never reformatted.

A successfully booted CURRENT may replace PREVIOUS only when its exact
manifest, file contents, version and installation match state.r4s. Its copy
must pass flush/readback while CURRENT remains intact, before the separate
CURRENT replacement starts. Unconfirmed CURRENT cannot displace PREVIOUS;
the running Previous slot is preserved. Obsolete slot files are removed.

The kernel records its actual Limine ELF identity and the runtime hash
verified before RAM mounting. After menu initialization, the application
checks these facts against CURRENT and persists the content-bound boot
confirmation. Failure to save it leaves the RAM session available. New
packages also bind the kernel to its exact runtime through Recovery-owned
ELF metadata. Limine uses fixed Current/Previous entries and ignores state.

A write failure is reported as incomplete and leaves the target unmounted.
Previous is selected manually for repair. Shared FAT32 or BOOT corruption
still requires a separate USB; no atomic directory swap or general power-loss
recovery for the shared filesystem is promised by these file update plans.
