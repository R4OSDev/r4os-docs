R4OS filesystems and storage
============================

Layers
------

- R4D storage drivers register block devices.
- The block core owns stable device slots, request queues, workers and
  completions.
- The page cache owns cached sectors/pages, dirty state and writeback.
- The VFS dispatches mounted filesystems.
- NTFS is the normal system-volume format. FAT32 remains supported for
  additional media and compatibility.
- R4SYS exposes drives, directories, files, streams and atomic update
  operations to programs.

Partition discovery
-------------------

The boot-time scanner supports DOS/MBR and GPT partition tables on devices
with 512-byte logical sectors. A protective MBR selects GPT exclusively, so a
hybrid table cannot expose the same partition twice. GPT headers are accepted
only after their signature, revision, size, reserved field, header CRC,
primary/backup placement, usable range and bounded entry geometry validate.
The complete partition-entry-array CRC is checked before any entry is used. If
the primary header or its entry array is invalid, the scanner retries the
backup header and backup entry array at the end of the device.

EFI System and Microsoft Basic Data partitions are mount candidates. The ESP
uses the FAT32 path; Basic Data is probed for NTFS first and FAT32 second.
Unsupported GPT type GUIDs remain visible in the boot log but are not mounted.
For a managed GPT installation, the actual Limine executable disk/partition
GUIDs and BOOT:/boot/r4os-installation.json select that installation's SYSTEM
as `C:`, DATA as `D:` and BOOT as the internal, unlettered boot volume. All
three filesystem roles are checked before publication. Other attached
installations receive only additional letters from E: onward. Missing,
conflicting or cloned boot identities fail explicitly instead of selecting
the first recognizable system tree.

FAT32 volume-label entries are metadata, not filesystem objects. Lookup,
mutation lookup and directory enumeration skip them; a volume labelled BOOT
can contain a distinct boot directory. This normal-owner fix is also frozen
into Recovery. Installer-created BOOT uses the Distribution label R4OS BOOT
for compatibility with older release kernels; the GPT role remains BOOT.

The pre-0.76 two-partition MBR image remains supported through its nonzero,
unique actual Limine disk signature. Its identified disk is scanned first;
only this explicit legacy path uses filesystem-neutral R4OS tree markers.
A GPT identity failure cannot enter the legacy path.

Legacy mounts carry both the start LBA and the selected partition length into
FAT32/NTFS inspection. Empty, zero-start, overflowing or device-exceeding table
ranges fail before signature or filesystem reads; byte-size overflow is also
rejected before mounting. The FAT geometry and NTFS device seam remain bounded
by that partition, even when the physical device continues into another one.
An explicitly unpartitioned filesystem at sector zero is a separate
whole-device probe; a partition-table entry is never treated as that fallback.

The current filesystem adapters still require a partition start within the
32-bit LBA range. Devices with another logical-sector size and partitions
beyond that start limit remain registered at the block boundary but are not
mounted through this scanner.

Every boot scan retains a bounded result record until the shell admission
boundary. If no system volume became `C:`, the fatal screen reports detected
AHCI/NVMe controllers, registered block devices, backend ownership, sector
geometry, partition-table result, mount candidates, filesystem and R4OS
marker counts, block-read statistics and the R4D backend's last recovery
state. Marker lookup distinguishes a genuinely absent entry from a metadata
I/O failure. A volume with an uncertain marker result is therefore not
silently exposed as an ordinary data drive.

Block devices use stable tombstone slots. Unregister first stops new
admission and fails while mounts, operation pins, callbacks, queue entries,
locks or waiters still refer to the device. A successful unregister leaves no
live callback into the old driver.

The block core accepts one logically contiguous multi-sector transfer and
splits it, in order, at the registered backend limit. A zero limit means
unbounded. Writes report the exact successfully completed sector prefix;
the page cache invalidates only that prefix after a partial failure and keeps
the unwritten suffix intact. Drivers such as USB mass storage therefore keep
their small transport limit without imposing it on FAT32 or other callers.

USB mass storage dispatches CBW, data and CSW through the canonical USB-host
registry. The present transport remains a deliberately bounded BOT fallback:
queue depth one, LUN 0 only, reported maximum LUN 0, and no UAS or streams.
Its command payload is limited to 64 KiB. READ/WRITE(10) remains the compact
path while the complete request fits the 32-bit LBA range; READ/WRITE(16) owns
larger addresses. READ CAPACITY(10) is tried first and its 0xFFFFFFFF sentinel
selects READ CAPACITY(16), so capacities beyond 2 TiB remain 64-bit exact.

Each MSC medium owns its BOT transaction, status and command scratch buffer.
The generation-bound xHCI runtime stays pinned across CBW/data/CSW, recovery
and retry pauses. The controller owner only protects runtime selection,
rings and event routing; after the short polling grace a parked transfer
releases it and restores its exact device context on return. HID can consume
an already completed report on the same device or another device meanwhile.
Other tasks cannot reconfigure the pinned device. Disconnect closes new
admission and cancels the waiting transaction; Disable Slot and buffer
release follow after its owner exits. Controller shutdown defers while any
such transaction remains. The synchronous storage worker lane is unchanged.

The USB block device publishes the medium's actual power-of-two logical block
size from 512 bytes through 64 KiB and derives its per-request sector limit
from the 64-KiB transport bound. Thus 4Kn media are described and addressed
without 512-byte arithmetic. The current page-cache/filesystem mounting path
still accepts only 512-byte sectors; non-512 USB media remain visible at the
block boundary but are not falsely mounted through that older filesystem
adapter.

Runtime dispatch is owned per registered controller identity. Devices behind
one controller retain their ordered synchronous callback lane; independent
controllers have separate workers, so a sleeping backend callback cannot
hold up an unrelated controller. Worker creation failure falls back safely to
the primary lane and remains visible in the performance snapshot.

The version-2 R4D storage descriptor separates nonblocking submit from
completion. Its `queue_depth` is the hardware-owned in-flight limit; the block
core independently owns up to 16 waiting/active slots and selects their stable
request-ID order. Version-1 and null-submit descriptors remain on the
synchronous depth-one adapter, regardless of an older advertised queue depth.
No driver is parallelized merely by this contract.

NVME.R4D is the first hardware backend that implements the version-2 path.
During the pre-scheduler volume scan, its version-1 callbacks drive the same
DMA mappings, submission rings and completion drain synchronously. Runtime
workers switch the unchanged backend registration to nonblocking submit.
The driver scans all platform-supported NVMe functions and continuable active
namespace pages, negotiates SQ/CQ pairs, clamps each ring to CAP.MQES and
retains a valid one-command fallback. Namespaces share the negotiated queues
fairly; an inventory beyond the fixed platform capacity fails explicitly
rather than being truncated silently.

NVMe transfers use owner-bound segmented streaming mappings. PRP1 and PRP2
cover small requests; larger requests use one audited PRP-list page and are
bounded by MDTS and 2 MB. Multiple commands may be active with distinct CIDs
and generations. One publication pass rings each changed SQ tail once, and
one drain pass consumes all visible CQ phase entries before acknowledging the
new head. Timeout and cancellation use Abort first; controller reset changes
all ownership generations, completes accepted requests exactly once, rebuilds
the queues and requires an unchanged namespace inventory before reopening.
I/O completion queues use message vector zero. The PCI MSI/MSI-X route remains
disabled during the synchronous preload and is installed by the first
asynchronous runtime request. Each interrupt masks INTMS and, for MSI-X, its
table entry, schedules one finite Driver Work drain and acknowledges CQ heads
before unmasking; a raced generation receives at most one successor. Active
message-interrupt queues do not continuously repost work. Polling remains
bounded to preload, missing MSI/MSI-X or work capacity, timeout and recovery.
Reset and shutdown mask the source before queue mutation, and shutdown joins
work and unregisters the message route before bus mastering and DMA ownership
end.
After a successfully completed transport recovery, the synchronous early-boot
callback may replay the failed idempotent read exactly once. Command, media,
validation and DMA-preparation failures do not qualify, and writes are never
replayed automatically. A rejected completion also preserves its original
NVMe status plus PRP alignment facts in the backend diagnostic state.

AHCI.R4D implements the same version-2 ownership boundary for SATA. It scans
all supported AHCI functions and suitable SATA ports, performs IDENTIFY DEVICE
before registration and derives capacity, 512-byte through 4-KB logical
sectors, LBA range, cache/flush support, NCQ and drive queue depth. The usable
depth is the HBA/drive intersection clamped to 16 tags; a drive or HBA without
NCQ uses the same backend at depth one. Inventory beyond the fixed eight-port
platform capacity fails explicitly.

Initial discovery does not discard an implemented port from its immediate
post-reset PxSSTS value. The driver first stops command processing, installs
the command-list and received-FIS DMA bases, enables FIS reception and raises
POD/SUD while ST remains clear. It then waits for link presence, SATA
signature and a ready task file before starting the command engine and issuing
IDENTIFY. This ordering supports staggered-spin-up ports on real controllers
while still leaving empty ports unregistered.

Each AHCI request pins an owner-bound streaming mapping and converts it into
at most 64 PRDT entries, with a 2-MB request limit. NCQ uses the command slot
as its ATA tag. A completion owns a request only after both PxCI and PxSACT
have cleared that tag; a non-zero PRDBC must additionally report the full
transfer, while zero remains compatible with NCQ HBAs that do not update it.
IRQs capture status and delegate completion to finite driver-work passes,
while the same bounded drain polls when no route is available. MSI/INTx is
configured only at driver initialization, but HBA sources remain masked for
the synchronous pre-LAPIC boot phase and are armed by the first asynchronous
runtime request. Flush remains exclusive against all other tags.
Error-FIS, taskfile/link failure, timeout and cancellation close admission,
stop and COMRESET the port, complete old generations exactly once and require
an unchanged IDENTIFY result before reopening. Failed port quiescence
enters controller recovery. Once software preparation has ended, a failed port
stop still permits the HBA reset. All ports must then confirm quiescence before
old mappings are released. Unfinished preparation, a failed reset or unconfirmed
post-reset quiescence retain ownership and keep the backend closed.

Since 0.78.54, AHCI and NVMe synchronous reads/writes use private transfer memory
from admission onward. The SDK SharedDmaBuffer holds separate caller and device
references; the metadata page is outside the DMA payload. Writes copy into it
before submission, reads copy out only after an exact successful completion.
Retiring the mapping drops the device reference; returning drops the caller
reference. Failed recovery can therefore return an error without exposing reused
caller or block-adapter bounce memory to later DMA. A retained device reference
keeps its allocation until confirmed completion/quiescence, possibly permanently
if the device cannot be stopped. Flush needs no payload. This extra allocation
and copy apply only to synchronous callbacks, not normal asynchronous requests.
Completion and detach atomically claim the same generation; a late callback
cannot publish its result into a later synchronous call.

An accepted asynchronous request owns its exact generation handle and buffer
until one completion. The IRQ-facing callback only claims that handle; the
controller worker performs terminal accounting, wakes the caller and releases
owned bounce memory. Duplicate and late completions cannot address a reused
slot. Cancel is advisory. A successful reset is the only substitute for a
physical completion because it proves old commands quiescent before their
handles and buffers are retired.

Reads and writes may use all hardware slots, but a flush is an exclusive FIFO
barrier: earlier work drains first, the flush runs alone, and later work cannot
pass it. A timeout may detach a kernel-owned bounce buffer for late completion;
a direct resident borrower remains protected by its task unwind token until
completion or reset. Unregister closes admission and vetoes unload until every
operation pin, request, callback and waiter has quiesced.

The general block API treats caller memory as potentially pageable and uses a
bounded non-pageable bounce buffer. The page cache may select the explicit
direct API only while `io_busy` pins the exact PMM-backed cache frame, or for
kernel-owned stack/heap staging whose owner stays alive until completion. A
direct request never detaches after a timeout; it retains the borrower until
the synchronous backend callback returns. Direct, bounce, copy and timeout
counters are exported for verification.

Filesystem requests are serialized by the owning A-Z volume lane. Cross-drive
copy/move acquires only its two lanes in stable alphabetical order, while
owner-free stream cleanup conservatively acquires every lane. Long loops
cooperate with the scheduler; page-cache writeback does not replace explicit
durability points. Flush, atomic replacement and shutdown propagate backend
errors instead of reporting false success.

The checked ownership-transfer API additionally accepts the Contract flag
file_update_atomic_checked_flag_long_stage for forward FAT32 completion.
Its stage may have an existing long name; backup and newly created target
remain short names. The ordinary fileReplaceAtomic contract is unchanged.
The existing target/stage/backup fingerprints and physical identities are
checked under one filesystem request gate, including after the transition.

FAT32 removes and flushes the short owner entry before reclaiming its LFN
prefix, proceeding backwards through the prefix. Lookups ignore a validated
prefix ending at a deleted or unused short slot. Directory allocation
reclaims those orphan slots before reusing the short slot, so another file
cannot inherit the interrupted file's name. Invalid live LFN chains still
fail the strict lookup. Durable cache journals belong to the caller; this
ordering is not a general FAT journal or protection against torn sectors.

FAT file-chain release and random-offset traversal are bounded by the actual
volume geometry. The former 4096-cluster limit could leave allocated tails
after large-file deletion or address the wrong cluster on a distant read or
write. Release now checks FAT writes and the final free-space summary; a
range read must complete the entire requested range. Recovery's download
acceptance checks a 4100-cluster file, cold random reads/writes, neighboring
data, restored free space and an independent census of both FAT mirrors and
all reachable file chains. Interrupted reclamation still belongs to general
FAT repair; cache ownership ordering does not journal every allocator write.

Page-cache identities remain hash-addressed, while free slots and clean LRU
and dirty FIFO candidates use intrusive bounded queues. The 512 resident
metadata slots are a hard upper bound, but payload admission is adaptive. At
boot, one 4-KB cache page is admitted per 128 free physical frames, clamped
from 64 pages (256 KB) through 512 pages (2048 KB, or 2 MB). Current free-frame
pressure can reduce that RAM limit to 256 pages at 32 MB, 128 pages at 16 MB
and the 64-page floor at 4 MB; clean pages above the active limit are reclaimed
incrementally and dirty pages enter the existing writeback path. Clean and
dirty selection probes at most the eight block-device shards and prefers
eviction from the requesting device. Normal hit, slot, eviction, reclaim and
dirty selection therefore do not scan all 512 cache entries. A full entry scan
is reserved for device invalidation or an instrumented index-consistency
diagnostic; the latter is exported as a performance error counter.

The cache still admits device slots 0 through 7, although the block catalog
now admits 16 devices. Slots 8 through 15 cannot currently use normal cached
filesystem I/O; registration alone does not establish filesystem usability.

A bulk read spanning contiguous absent or partially valid cache pages reserves
and `io_busy`-pins those exact identities while holding the cache lock. It then
releases the lock once, issues one direct read through resident heap staging,
and reacquires the lock for an all-or-nothing publication. In 0.75.6 the run
length has a conservative two-page ceiling in addition to caller demand,
active cache capacity, available staging and the backend request limit. This is
the shape covered by FSDIAG and halves backend requests for aligned cold reads;
larger demand runs remain disabled after intermittent failures in the long
subsystem/AUTOEXEC workload. Only sectors absent at reservation time are
scattered into the pages, so valid or dirty bytes cannot be replaced by stale
media contents. A failed request publishes nothing, drops empty reservations
and wakes waiters through the established pin transition. USBMSC owns its exact
transport retry; other backends retain at most one cache-level retry.

Reads into program memory deliberately retain two measured copies. Cached
bytes first enter resident per-read staging while the cache identity is
protected; the cache lock is then released before staging is copied into the
potentially pageable caller buffer. Removing that second copy would require a
proven caller-page pinning contract. Without it, writing the caller directly
under the cache lock could fault back into storage and deadlock. Fill-run,
backend-request, page, sector, byte, failure, retry, scatter/caller-copy and
lock-release counters make this cost and the request reduction observable.

Each device activates dirty-pressure writeback at 64 pages (256 KB) and keeps
the pressure state until at most 32 pages (128 KB) remain. The batch-role
`pgcache-wb` worker also selects the oldest device FIFO head after a maximum
dirty age of two seconds. One activation writes at most four pages, issues
only one synchronous block request at a time and rotates fairly over devices.
A failed page remains dirty at the FIFO head and applies a one-second
device-local retry backoff, so one failing or heavily dirty device cannot
feed an unbounded request burst ahead of another device.

Background writeback establishes persistence progress but deliberately does
not issue a backend flush barrier. Explicit whole-device, operation-batch and
shutdown flushes still drain their complete ownership set and then call the
backend barrier. They wait for a target-device dirty page already pinned by
background I/O, so the temporary queue detachment cannot create a false clean
result. Reclaim never discards dirty data, and device invalidation cancels
speculative work before draining and removing the device identities.

Speculative read-ahead is deliberately disabled in 0.75.6. Adaptive and
single-page variants were exercised against the subsystem/AUTOEXEC workload
after contiguous demand fills were introduced; every variant reproducibly
stalled that workload, while two-page demand-only fills completed it and
combined 256 cold pages into 128 backend requests. R4DEV therefore reports both read-ahead
window values and all activity counters as zero. The bounded sequential model
remains unit-tested but is not allowed to issue I/O until a future change can
explain and eliminate the interaction. Dirty progress and capacity contraction
remain the only page-cache worker jobs.

Regular FAT32 mutations tag every cached dirty sector with an operation-local
write batch. Their commit writes only that batch, including selected sectors
inside an otherwise foreign-dirty 4-KB page, and then issues the unchanged
backend flush barrier. Deferred stream dirties and unrelated mutations remain
cached. Recovery, idempotent lost-completion reconciliation, atomic ownership
transfer and explicit public volume flushes deliberately retain the stronger
whole-device-cache drain before the same barrier.

The kernel NTFS adapter preserves contiguous writes larger than one sector as
bounded multi-sector direct page-cache submissions. The direct path stages
resident ownership, pins all overlapping cache identities and invalidates
only the backend-confirmed prefix on partial failure. The shared NTFS volume
core still owns write ordering and calls the unchanged flush seam at each
durability boundary.

Decoded NTFS metadata is cached separately from sector payloads. In cache
version 2, each mounted NTFS volume owns exactly eight fixed MFT-record slots, four decoded
attribute/runlist slots, two decoded INDX-block slots and eight positive or
negative path-component slots. Entries are tied to the mount and content
generation; negative entries expire after one second. The normal path cache
uses the volume `$UpCase` collation, while recovery-only transient lookups
bypass it.

Every NTFS write is classified before its first physical sector can become
visible. Pure file payload writes retain all decoded metadata. Primary MFT
record writes remove only that record, its decoded attributes, any directory
index owned by it, and positive or negative paths derived from the record or
directory. Non-resident attribute writes carry their record and attribute
type; directory-index writes carry their directory record and remove only its
decoded INDX blocks and paths. The fully classified MFT mirror is not a source
for live decoded entries and therefore also retains the cache. Unknown and
recovery/ambiguous rollback mutations remain conservative whole-cache
invalidations; mount and explicit media-generation changes keep their own
global invalidations. Targeted invalidation does not advance the global
content generation, so unrelated entries remain reusable while stale
positive and negative results are removed by identity.

R4DEV PerformanceSummary v14 reports retained payload and system writes,
targeted record/attribute/directory requests, global and recovery requests,
and the exact number of removed record, attribute, index and path entries.
The shared host hardening model covers unchanged in-place payload writes,
Append/Resize, Rename, Delete and recovery after partial failure; FSDIAG
repeats the namespace transitions in the running guest. Global reclaim drops at most
eight decoded entries per request and examines at most 22 slots in each of
the four fixed mount slots. The fixed cache control storage remains resident
and never owns page-cache sectors or a second file payload.

NTFS cluster allocation plans the complete run set before changing $Bitmap.
If a bitmap update fails, all possibly written ranges are rolled back. Abort
cleanup releases records and clusters in an ownership-safe order; a failed
rollback or dirty clear is reported explicitly and leaves the volume dirty,
so incomplete cleanup can never be certified as a clean filesystem.

NTFS free-space queries (Kernel 0.1.103)
---------------------------------------
DriveInfo keeps an exact free-cluster count in the existing mount-owned
metadata cache. The initial scan reads $Bitmap in at most 64-KB blocks using
the volume scratch and counts whole words, excluding padding beyond the last
cluster. A short or uninitialized bitmap and an incomplete read do not publish
a count. Repeated queries need no bitmap reads or recounting.

Allocation and release update the count by the number of bits actually
changed in each successfully written bitmap sector. The old count is
invalidated before writing; an ambiguous failure never restores it. Remount,
external changes, direct bitmap metadata changes and recovery invalidate the
count. Unrelated file data, namespace changes and decoded-entry reclaim do
not require a new scan. The existing filesystem request owner serializes all
these operations; no second bitmap or disk-format change is introduced.

Exclusive maintenance and mounted uses (0.76.8)
----------------------------------------------
storage/access_state owns bounded, generation-bound device registrations,
mount incarnations, call/transfer uses and region claims. access_runtime
serializes only their metadata under the storage owner. No driver, VFS,
cache wait or scheduler work runs while this short owner is held.

storage/operations implements the public mechanism with a separate sleepable
orchestration gate. Normal filesystem requests acquire their actual backing
mount before waiting; copy/move bind both sides and write streams keep a use
until finish/abort/retirement. Required C: and the internal boot volume reject
maintenance. Recovery instead runs from RAM C: and mounts physical BOOT as
an ordinary offline volume. Claims cover the complete disk or partition;
new overlapping requests fail, while unrelated volumes keep working.

The cache drains busy entries, writes only dirty sectors in the affected
range, invalidates only that range and flushes the backend. This includes
partitions sharing a cache page. Claim completion performs another flush,
rescans the table and reprobes matching saved mount identities. FAT allocation
caches and NTFS runtime volume state are forgotten only after detachment.
A failed flush/remount is reported and leaves the target visible, unmounted
when required. The cleanup worker performs final I/O after owner retirement,
following existing asynchronous-call and stream drains.

USB BOT now binds its internal device handle to the xHCI enumeration
incarnation. Disconnect/reconnect or changed-medium SCSI sense permanently
invalidates the old block registration before another write is dispatched.
Transport reset alone cannot silently associate that registration with a
replacement medium. Public USB module layouts stay unchanged.

Shared maintenance tools (0.76.9)
--------------------------------
SDK/r4os/storage_tools is the owner of hostneutral partition creation/editing
and FAT32/NTFS formatting. The ImageCreator reuses its geometry and NTFS
builder; Recovery and later R4PART execute the same logic using public R4SYS
claims. The kernel owns physical admission and mounted filesystems, while
partition commands, formatting policy and installer decisions remain userland.
512-byte geometry, bounded I/O, generation/fingerprint checks, ordered flush
and readback protect this boundary. Large volume formatters stream their
metadata; the legacy complete-image return remains for existing image trees
until the five-partition distribution plan replaces that orchestration.

Partition identity changes (0.76.10)
------------------------------------
Claim completion restores only surviving disk GUID/MBR ID, partition number,
bounds, unique GUID and type. Deleted or reidentified partitions do not inherit
old letters or installation roles and are not remount failures. A matching
identity with a damaged filesystem still reports a real remount failure.
R4PART OFFLINE flushes/detaches affected mounts with KEEP_UNMOUNTED; this
survives application EXIT. ONLINE explicitly mounts them again and does not
change device power or prevent another explicit mount.

Offline NTFS growth (0.76.11)
---------------------------
R4PART EXTEND uses SDK storage_tools.ntfs_extend with an exclusive whole-disk
claim for the table change. The partition starts and IDs stay fixed. The
prepared metadata plan relocates the cluster bitmap into adjacent new space,
updates MFT/root duplicated sizes and $Bad, then publishes both boot sectors.
Dirty marking, table/bitmap/metadata/boot publication and final clean marking
have explicit flush/readback barriers. The plan and working buffer are bounded;
bitmap size does not become a volume-sized RAM allocation. Fingerprints are
rechecked after unmount and before writes. No automatic power-fail rollback.
Unsupported/dirty layouts and busy volumes reject before mutation; interruption
can require external NTFS/table repair. SDK/DOCUMENTATION.de.txt specifies the
accepted geometry and actual persistence windows. On success R4PART restores
only the resized target at its former letter after a fresh identity check.
The kernel's generic identity/size restoration rule remains unchanged.

Offline NTFS shrink (0.76.12)
---------------------------
SDK storage_tools.ntfs_resize owns both directions (ntfs_extend is a compatible
alias). SHRINK QUERYMAX scans the actual bitmap and active MFT attribute runs;
fixed file/metadata clusters, real replacement-bitmap space and a 16-MB floor
set the executable maximum. The bitmap may move; file data and other metadata
stay at their LCNs. A bounded bitmap cache validates run allocation and rejects
references shared with the retired bitmap. The MFT and the bitmap used for the
query are fingerprinted and rechecked before writes, for either resize direction.
The accepted profile has no attribute-list/extension records and at most one
million MFT records; metadata runs retain their tighter bound. This is not a
complete filesystem repair or defragmenter. The SDK owner contract lists limits.
SHRINK DESIRED=MB removes exactly the requested amount, or without DESIRED the
current maximum. The smaller filesystem and both boot copies become durable
before the smaller GPT/MBR boundary; clean marking and remount require both to
succeed. Failure leaves the affected target unmounted with its actual progress.

GPT inspection/repair and R4PART scripts (0.76.13)
------------------------------------------------
SDK storage_tools.gpt_repair.Report independently checks both GPT headers and
arrays, CRCs, geometry, partition identities and overlaps. R4PART CHECK GPT
requires matching intact copies. REPAIR GPT restores only a damaged counterpart
from a unique intact copy; conflicting/invalid sources or I/O ambiguity refuse.
Under the whole-disk claim it revalidates the full observed SHA-256 fingerprint,
then writes/flushes/verifies the bad array before its header. The good copy,
protective MBR and partition payload remain untouched. Accepted geometry and
counterpart placement are documented in SDK/DOCUMENTATION.de.txt.
R4PART /S preloads at most 64 KB UTF-8, with 512-byte lines and optional BOM.
It uses the same commands and explicit confirmation lines; first error/EOF at
a required confirmation stops with code 1, success/EXIT returns 0. It retains
no script file handle during mutation. Failed SELECT clears prior selection.

NTFS-Arbeitsbuffer und parallele Volumes (0.76.13)
----------------------------------------------
Die fs-request-Sperren gelten pro Laufwerk. Jedes gemountete NTFS-Volume
besitzt deshalb neben MFT-Runs und Metadatencache einen eigenen Heap-Buffer
fuer Record-, Attribut-, Index- und Kompressionsarbeit. Ein globaler Buffer
wuerde parallele Zugriffe auf SYSTEM und ein anderes NTFS-Volume vermischen.
Die Allokation erfolgt beim Mount direkt im Heap, ohne grosse Stackkopie;
fehlgeschlagener Mount und letzter Unmount geben Buffer und UpCase frei.
Ein erneutes Inspect einer bestehenden Mountidentitaet nutzt deren Zustand,
ohne live Metadaten neu einzulesen. Storage-Mount verweigert ueberlappende
weitere Laufwerkszuordnungen; ein Austausch erfordert den bestehenden Drain-
und Forget-Pfad. Die Dateisystemsperren bleiben nach Laufwerken getrennt.

Verzeichnis-Aenderungshinweise (0.78.26)
---------------------------------------
R4SYS stellt zwei optionale Anhaengeslots bereit: directory_change_begin
und directory_change_poll (R4SYS-Tabellenrevision 17, Query-Import unveraendert).
Begin loest das Verzeichnis unter dem FS-Request-Gate auf und erfasst
Mount-Slot, Mount-Generation, Node und Aenderungssequenz. Poll prueft nur
RAM; der caller-eigene Cursor reserviert weder Handle noch Watcher-Slot.

Der VFS publiziert nach schreibenden Operationen einen Hinweis fuer den
Elternknoten, vorsorglich auch nach einem moeglichen Teilfehler. Range-Write
und Stream-Finish melden den bereits aufgeloesten Elternknoten ebenfalls.
Die 256 Eintraege grosse Historie liegt unter einem kurzen Storage-Owner;
der Desktop-Aktivitaetsweck erfolgt erst nach dessen Freigabe. Andere
Verzeichnisse und fremde Mount-Generationen werden unterschieden. Ueberlauf
fordert konservativ einen neuen Lauf an. Unmount weckt wartende Ansichten;
ein pensionierter Mount meldet Fehler.

Dies sind Hinweise fuer direkte Verzeichniseintraege und deren Dateiinhalte,
kein rekursiver Watcher und keine atomare Mehrseiten-Dateisystemsicht.
Verbraucher muessen Enumerationsergebnisse weiterhin auf Fehler pruefen.


NTFS-Fixups und Spiegel-Bootstrap (0.78.30)
-----------------------------------------
FILE- und INDX-Records muessen exakt einen Fixup-Eintrag je vollstaendigem
512-Byte-Sektor plus das Update-Sequence-Wort enthalten. Apply und Install
weisen zu kurze oder nur teilweise abgedeckte Records vor einer Mutation
zurueck; der USN-Vergleich prueft auch den letzten Sektor.

Mount validiert zuerst den primaeren MFT-Record 0 einschliesslich Fixups,
Recordidentitaet, Attributgeometrie und MFT-Runlist. Ist dieser Kandidat
ungueltig oder nicht lesbar, wird genau der Record 0 am Bootsektor-Ort
von $MFTMirr mit denselben Regeln versucht. Der erste Datenrun muss zur
primaeren MFT gehoeren. Ein gueltiger Primaerrecord hat Vorrang; ein
ungueltiger Spiegel verhindert seinen Mount nicht. Sind beide Kandidaten
ungueltig, scheitert der Mount ohne Schreibversuch.

Ein Spiegel-Bootstrap setzt MountInfo.used_mft_mirror und haelt dessen LCN
im mount-eigenen Scratch. Spaetere Record-0-Lesevorgaenge verwenden weiter
diese Kopie. Andere Records werden normal aus der primaeren MFT gelesen
und validiert; der Fallback verdeckt keine Schaeden ausserhalb Record 0.
Der Kernel meldet diesen Mount als read-only (MFT mirror bootstrap; repair
required). Nutzdaten-, Record- und Sektorschreibpfade sowie normale
Saubermeldung sind gesperrt. Der Mount repariert weder die Primaerkopie
noch bestaetigt er eine veraltete Spiegelkopie als aktuellen Datenbestand.
Die bestehende allgemeine Behandlung schon schmutziger Volumes bleibt
getrennt von diesem ausschliesslich lesenden Fallback.
