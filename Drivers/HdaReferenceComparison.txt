HDA reference comparison for R4OS 0.67.X
========================================

Reference set
-------------
The reproducible, SHA-256-checked source archive is local at
ExFiles/Reference/Hardware/HDA/. Download-References.ps1 verifies 20 files:
Intel HDA 1.0a, Intel HDA033-A and HDA043-A, QEMU commit
a4bb4b10c9d43d416f6e8bc9bb5c8f372fd80769, and Linux stable commit
2609d60e2f6d0b8a96563baa08b56482962cebaa. These files are development
references and are not shipped in R4OS images.

Root cause
----------
R4BASIC and r4os.subsystem_runtime submit 480 frames, or 1,920 bytes, every
10 ms. The previous HDA driver placed each packet in a 4,096-byte BDLE and
zeroed the remaining 2,176 bytes. At stereo S16 that is exactly 544 unwanted
zero frames after 480 useful frames. BEEP.R4X happened to write 1,024-frame
blocks and therefore concealed the general defect; R4BASIC never routed its
BEEP statement through BEEP.R4X.

Validation
----------
- stream_ring.zig host tests cover wrapped byte queues, producer ownership,
  missing periods, recovery and cyclic wraparound.
- AudioDiag pattern tests cover nonzero samples and phase preservation across
  packet boundaries; long-mode pacing follows the published HDA fill level.
- Analyze-QemuWav.ps1 selftests reject injected 480/544, sample-loss and
  internal-silence fixtures.
- Standard-QEMU short capture: 8,280 input frames, continuous signal,
  Known480_544Patterns=0, all path error counters zero.
- Standard-QEMU long run: 2,880,000 frames, 6,000 writes, all path error and
  silence counters zero. Long-mode feeding follows HDA fill level so QEMU
  guest-clock drift is not misreported as a hardware-ring underrun.

Open hardware row
-----------------
The Lenovo IdeaPad L340-15API still needs a cold-boot record with PCI codec,
MSI/INTx route, LPIB behavior, five-minute tone, repeated start/stop/close,
BEEP.R4X and R4BASIC BEEP/PLAY. Until that run exists, QEMU evidence must not
be described as a physical HDA acceptance.
