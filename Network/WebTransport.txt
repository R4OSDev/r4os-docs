R4OS web transport
==================

The SDK web facade composes existing owners rather than providing a private
browser stack:

- R4NET and network services: DNS, TCP, timeouts and backpressure;
- R4HTTP: bounded HTTP/1.0 and HTTP/1.1 parsing, redirects and streaming;
- R4TLS: TLS 1.2, certificate-chain and hostname validation;
- the application: response storage, navigation, display and cancellation.

HTTP bodies can be consumed incrementally. Redirect limits, header/body
budgets, content length, chunked transfer and connection close are explicit
states. Relative timeouts are converted once to an absolute monotonic
deadline so repeated phases cannot reset the budget.

The first deadline is acquired only after the target authorizer accepts a
parsed URL. Rejected targets, invalid URLs and an already cancelled request
do not access the transport clock or open a connection. The same rule applies
to buffered fetch and streamed download; redirects keep the original budget.
Extra headers use the SDK's LF-separated input format. The facade adds the
wire CRLF framing, User-Agent and identity content encoding itself.

Cache metadata since 0.78.46 uses separate conditional_headers and
cache_headers fields in FetchOptions. Both use the same LF-terminated header
format and are concatenated without empty lines. Author headers alone drive
CORS preflight; generated validators apply only to the initial request, while
cache directives follow redirects. initial_cookie freezes the first request's
cookie value for an exact cache key. Later hops continue to use the caller's
cookie provider. The bounded HTTP response cache belongs to Klickifax and is
described in Browser.txt; other web transport users retain uncached fetch.

Buffered transport since 0.78.47
--------------------------------

ResponseDecoder tracks headers, chunk sizes, partial payloads, CRLF and
trailers across monotonically growing input in stable caller buffers. Each
payload byte is copied into the body buffer once. Content-Length and close-
delimited bodies use the same progress state; only EOF ends the latter.
Informational responses are consumed before the final response, with a bound
of eight; protocol upgrades remain unsupported. Trailer fields do not alter
framing or the accepted response headers. The one-shot decoder remains a
wrapper over this state machine. The separate streamed-download path keeps
its existing Content-Length contract.

FetchOptions.sessions opts into a caller-owned SessionPool. Each pool retains
at most two connections and four accepted CORS preflight results. Connections
are keyed by scheme, host, port, origin, network partition and credentials
mode; HTTPS retains the actual TLS stream state. An HTTP/1.1 response is
reusable only after its exact, self-delimited end. HTTP/1.0, close-delimited
responses, Connection: close, upgrades, extra trailing bytes, errors and
cancellation retire the connection. Idle connections expire after 30 seconds.
GET/HEAD can retry a failed write to a reused connection once under the same
absolute deadline. Explicit Connection/Upgrade request headers and requests
without a pool keep the one-shot path.

Preflight entries include partition, origin, full URL, credentials and the
requested method/header names. Max-age is capped at 600 seconds, defaults to
five seconds when absent or invalid, and zero disables retention. A wildcard
does not authorize the Authorization header. Request variants never borrow
another entry's result. TransportStats count actual resolver calls, connects,
TLS handshakes, reused connections, preflights and decoded payload copies.

app_web_jobs.Job owns one program thread, stop flag, session pool and response
result. Callers bound their live job set to app_web_jobs.capacity (two).
Cookie and target-authorization callbacks are handed back to the owner loop;
workers do not call GUI, Runtime, DOM or cache code. The owner must service
callbacks and collect the thread before freeing or reusing borrowed storage.
Cancellation also drains published callbacks; cancelled responses are never
reused. Progress/event pumping stays in the owner loop. Each job keeps its
original absolute request deadline through redirects and retries.

web_runtime_jobs.RequestJob freezes request headers/body, URL, origin and
credentials into owned buffers and keeps independent response/TLS workspaces.
Completion resolves the current Runtime by generation and checks every cohort
consumer's request ID. Retired subdocuments therefore cannot leave a borrowed
Runtime pointer in a worker. The browser prepares/finishes cache transactions
on its owner thread and pins old cache entries across a network operation.

References: https://www.rfc-editor.org/rfc/rfc9112.html#name-persistence
            https://fetch.spec.whatwg.org/#cors-preflight-cache

Recovery uses this same DNS/TCP/R4HTTP/R4TLS path for the two public GitHub
release channels. It accepts the matching stable asset, follows only approved
HTTPS hosts, streams at explicit offsets into the boot volume's PART file,
and verifies the GitHub SHA-256 plus the complete package before publication.
Its cache transaction belongs to RecoveryTools, not to the web transport.
The public trust catalog includes USERTrust RSA and ECC roots, required by
the observed GitHub/Sectigo certificate chains. These roots are explicitly
imported into Recovery; the frozen TLS binary and certificate checks remain
the same. A later trust-store change still requires a deliberate owner import.

The current stack is deliberately not a claim of full modern-browser network
compatibility. HTTP/2, HTTP/3 and unsupported TLS algorithms remain visible
limitations rather than triggering a host proxy or site-specific bypass.


Remaining close ownership boundary (0.78.58)
------------------------------------------
The network facade now verifies truncated/invalid close replies and retains
the socket for a retry. A controlled timeout followed by a confirmed retry
is covered in both Zig and C. SessionPool.closeEntry still resets its entry
after its bounded best-effort close; temporary WebTransport fetches similarly
discard a local socket on return. Thus an unconfirmed close can still lose
the caller's retry reference. No reliable owner queue or automatic cleanup
for this case is claimed. The caller lifetime change remains a recorded
follow-up; extending every network operation with unbounded waits is not a
solution. No such timeout was observed in the successful local echo guest.


HTTP-/URL-Grenzen ab 0.78.70
---------------------------
Pfad und Query duerfen weder rohe Steuerbytes noch Leerzeichen in die
HTTP-Anfragezeile uebertragen. Parse und Build pruefen diesen Vertrag;
vorhandene Prozentkodierung bleibt erhalten, UTF-8 und weitere nicht direkt
zulaessige URI-Bytes werden beim Serialisieren kodiert. Zusaetzlich werden
direkt erzeugte Hostfelder und Namen eigener Requestheader geprueft.

Ein Fragezeichen nach dem Fragmentanfang gehoert zum Fragment. Die bereits
gemeinsam angebundenen URL-/Location-/Origin-Verbraucher verwenden die
korrigierte Zerlegung. Navigation und Redirects nutzen einen gemeinsamen
Aufloeser; nur ganze Punktsegmente verschwinden, doppelte Slashes, kodierte
Punkte sowie Query-/Fragmentinhalt bleiben erhalten. HTTP behaelt seine
caller-eigene Ausgabekapazitaet statt das Browserlimit zu uebernehmen.

Vollstaendige ungueltige Antwortkoepfe melden ihren konkreten Grund:
Status, Version, Headerform/-zahl, Content-Length, widerspruechliche Laenge
oder Transfer-Encoding. Ein spaeteres EOF verdeckt den Fehler nicht.
Unvollstaendige Koepfe bleiben davon unterscheidbar. Auch eine gueltige
Antwort ohne Headerfelder wird akzeptiert; dieser Randfall war vorher
irrtuemlich abgewiesen beziehungsweise hatte einen ungueltigen Ausschnitt.

Sechs kurze Hostfaelle fuer echte Parser/Serializer sind ausreichend.
Kein zusaetzlicher Netzwerk-, QEMU- oder Browser-Gesamtprofiltest. R4HTTP
0.1.4, R4JS 0.54.11, Klickifax 0.29.19, KlickifaxLive 0.2.20 und UpdateService
0.2.19 werden mit der Korrektur gebaut. Recovery 0.1.54 / Menue 0.1.19 erhaelt
den gleichen bestaetigten HTTP-/URL-Quellstand und das R4HTTP-Artefakt.
