R4OS workspace build and test
=============================

The workspace root coordinates independent repositories. The normal entry is
`Tools\Build.bat` on Windows and `./Tools/Build.sh` on Linux; without
arguments either starter displays an interactive menu.

Common modes
------------

- `-central`: Contract, SDK and Runtime-R4Ls.
- `-kernel`: kernel only.
- `-modules`: every App, Service, Diagnostic, Driver, Protocol and Subsystem.
- `-module <Role\Project>`: one module repository.
- `-all [Slim|Full|Test]`: complete build and image.
- `-gui`: complete Full build, image and visible QEMU.
- `-test`: complete Test build, verified image and SMP4 headless acceptance.
- `-testsmp`: run the existing Test image with four QEMU CPUs.
- `-qemu <Profile>`: run an existing image without rebuilding it.

The root build does not implement a second image builder. It builds component
repositories, creates explicit workspace/common/profile plans and delegates
image creation and QEMU to `Repositories/Distribution/`.

Since 0.78.7, profile builds first select manifests using the same rules as
the image plan, including explicit Test/Browser/Benchmark targets and
dependency-closure validation. Selection works before artifacts exist.
Only selected direct module owners are built; Contract, SDK, Libraries and
Kernel retain their central build order. IMAGE_SCOPE=none remains opt-in.
The current direct starter counts are Slim 42, Full 97, Test 99 and
Benchmark 98, compared with 138 for each former regular profile build.
An explicit browser test selects 105 owners; -modules still selects all 140.

The Distribution starter additionally accepts `headless Test clock4`,
`headless Test smp4` and the diagnostic partial-failure variant
`headless Test smpfail4`. The last variant requires a kernel built with the
private `-Dsmp-fail-ap-index=2` seam and is not a normal product build.

Outputs
-------

Module artifacts are placed below `Artifacts/Modules/`. Distribution plans,
generated inventories, images and logs are placed below
`Artifacts/Distribution/`. A profile's boot image is
`Artifacts/Distribution/Profiles/<Profile>/disk.img`, sealed by `image.json`.
All four profiles (Slim, Full, Test, Benchmark) use BIOSBOOT/BOOT/SYSTEM/
RECOVERY/DATA in this single image. GUI/SSH keep their state in
`Interactive/<source-SHA256>/disk.img`; automated runners create a fresh copy
under `Runs/<name>/disk.img`. They reject a modified canonical source.

The detailed developer workflow is maintained in the workspace agent
reference `Agents/Build.txt`. Individual tests are inventoried in
`Docs/Inventory/Tests.json`.

Common installation image (0.76.22)
----------------------------------

After building the normal components,
`Repositories/Distribution/Build.sh image Slim` produces
`Artifacts/Distribution/Profiles/Slim/disk.img`. Windows uses the .bat
starter; all orchestration is shared PowerShell 7. `RecoveryPin.json` must
select a published version, release ID and SHA256. A cached exact package
works offline. An explicit `-RecoveryCandidate <ZIP>` selects a local
technical input; no image build implicitly updates or rebuilds Recovery.
`-Medium usb` selects Recovery as the five-second Limine menu default.

This 2048-MB GPT image has BIOSBOOT 1 MB, BOOT 128 MB FAT32/ESP,
SYSTEM 1024 MB NTFS, RECOVERY 512 MB FAT32 and DATA NTFS in the actual
remaining usable sectors. Both GPT copies, new IDs, installation JSON and
Limine references are checked independently, including the physical FAT
allocation and the complete initial CURRENT/PREVIOUS package contents.
`image.json` records source hashes and distinguishes technical candidates
from the published pin. Release preparation reformats DATA in a private
copy, includes the independent Recovery ZIP and standalone USB creators,
and verifies image/manifest/BOOT/Recovery agreement. The source image has
no original-ZIP cache: the USB creator adds that after writing the image.

ImageCreator's create-installation path now writes to a private file and
atomically replaces the destination only after successful publication and
read-back. FAT uses prepared metadata and borrowed file segments; NTFS uses
its existing streamed plan. Input payloads remain resident per partition,
but complete image/volume buffers are avoided. NtfsVerify reads bounded
partition views through one shared-locked file handle; structural metadata
still scales with filesystem complexity. Its MBR views now also respect the
partition length. Legacy standalone ImageCreator compatibility modes retain
their existing in-memory behavior.

Release packaging combines the canonical-image copy with its SHA256 check,
keeps one private fresh-DATA image, and holds that image open from structure
validation through ZIP output. Compression computes manifest hashes from
the bytes it writes; staging no longer contains a second disk.img. This
reduces the package phase from five to two complete image reads and from two
to one complete private image copy per profile, in addition to required
region checks. Prepared publication continues to use the exact ZIP bytes.
The 0.78.7 Linux Full-image check measured about 227 MB maximum RSS for
ImageCreator and 11 MB for NtfsVerify (previous verifier: 2050 MB). These are
host measurements, not hardware or guest performance claims.

Recovery has independent `Release.sh` / `Release.bat` starters for Prepare,
Publish and SelfTest. Prepare records the frozen component inputs and
requires the named kernel/runtime pair to match. Technical local packages
use `-Technical`; a normal R4OS preparation accepts them only through
`Tools/Release.ps1 -TechnicalCandidate -RecoveryCandidate <ZIP>`.
Neither publisher accepts technical mode.

`pwsh -NoProfile -File Repositories/Distribution/Tests/Test-InstallationImage.ps1`
performs the bounded SMP4 BIOS/UEFI acceptance, including multiple
installations, damaged SYSTEM, USB default and ambiguous IDs. All guests use
snapshot overlays, and every base image is hashed again after the runs.


Recovery integration and published channels (0.76.24)
---------------------------------------------------
Recovery's shared Guest-Qmp.ps1 supplies
`-fw_cfg name=opt/org.seabios/pci64,string=0` to its BIOS NVMe UI/install/update
acceptances. SeaBIOS 1.17 with QEMU 11.0.2 otherwise moves that controller's
BAR above 4 GB and cannot boot it at the qualified 8-GB RAM size. The same
Full image boots normally with this setting; OVMF ignores the SeaBIOS key.
This is a host firmware configuration, not a change to R4OS or real hardware.

The bounded SMP4 integration combines existing UI, network/storage/R4PART,
install/update and download-failure evidence. Its artifact-bound report is
`Repositories/Recovery/Artifacts/Qualification/0.76.24/report.json`.
Only one automated guest runs at a time. No benchmark or browser run is added.

After an actual public release, run
`pwsh -NoProfile -File Repositories/Recovery/Tools/Test-PublishedRelease.ps1
 -Product Recovery -Version <version> -Sha256 <published ZIP SHA256>
 -BaseImage <verified uncached common local image>` on one line.
Product R4OS additionally takes `-Profile Slim|Full`. This uses the production
menu through a USB keyboard to download the complete actual latest asset.
It verifies the cache independently and preserves every unrelated partition.
The initial image is copied. Recovery runs in 0.76.25; final R4OS follows only
after the single Lenovo USB-boot/local-install acceptance in 0.76.26.

After qualification, `Repositories/Distribution/Release.sh -Action Publish
 -Profiles Standard -Prepared` publishes the exact prepared ZIPs. It verifies
their checksums, source revisions and published Recovery pin without rebuilding
images or archives. Modified assets, sources or pins require a new preparation
and appropriate qualification. Omitting -Prepared retains the combined
prepare-and-publish command; use -Prepared after the final Lenovo acceptance.
