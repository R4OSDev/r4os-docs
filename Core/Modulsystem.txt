R4OS module system
==================

R4M0 is the common container for R4X applications and services, R4L
libraries, R4D drivers and R4P protocols. The formal format is owned by
`Repositories/Contract/ABI/R4M0.txt`; project metadata is owned by
`Repositories/Contract/Module/R4MFv2.txt`.

File containers use kinds 1 through 4. Kind 5 is reserved for the six
built-in Platform API provider identities and kind 6 for a possible Kernel
module; neither is accepted from a file. R4SYS through R4DEV therefore have
no R4L container, manifest or image entry.

A container can hold code, read-only data, writable data, imports, exports,
metadata, relocations and named resources. The loader validates every range
before publishing the module. The relocation table is the only patch truth:
ordinary data values are never guessed to be old link pointers.

Loading
-------

1. Reserve a unique common slot and nonzero generation before the first
   waiting read. A task unwind token protects the complete preparation.
2. Validate header/tables and resolve imports in a private load workspace.
3. Allocate the image, copy sections and verify BSS before relocation and
   loaded-export checks; require executable R4D/R4P lifecycle exports.
4. Keep the image and exports private while the driver/protocol owner admits
   its descriptor and registry entry.
5. Publish the complete immutable entry with one release-store of its claim.
6. Enter the module-specific lifecycle such as R4XStart or DriverInit.

Since 0.78.51, R4D, R4P and boot Runtime-R4L dependency loading share the same
packed slot/generation claim. Independent driver/protocol gates therefore
cannot choose the same free common slot while one operation waits on I/O.
Readers acquire the publication claim before reading an entry. A reserved
entry is excluded from inventory, name resolution and public export lookup.
Successful entries remain resident, including the existing pinned Runtime-
R4Ls; abort only owns its exact unpublished generation. Repeated or stale
abort/commit handles cannot release or publish a later occupant.

Every failed read, allocation, BSS check, required export or owner admission
releases its private image, scratch and reservation. An unexpected heap-free
failure retains an inaccessible slot with its image reference for diagnosis;
it never offers that storage to a new load. No no-sleep lock spans file I/O.
Runtime driver unload still does not unmap an already admitted R4M0 image.

The per-load heap workspace owns the validated tables, resolved imports,
section offsets and one bounded metadata reader. Its two 4-KiB windows are
initialized in place by resetting only their validity metadata. Header,
tables, strings and relocations reuse that reader; requests larger than a
window and all section payloads still stream into their final image.
The fixed 8-KiB cache is independent of container size and no longer adds a
second reader or a by-value reader setup to the common loader's worker stack.
The normal IPC worker keeps its existing 64-KiB stack.

Import and export records and their names are validated once and retained in
the bounded load plan. Resolution, loaded-export validation and publication
reuse that plan instead of reading the file again. File bounds are checked
before I/O, short-read diagnostics include the exact offset, and all records
and relocations retain file order. A failed read, validation, relocation or
allocation still rolls back before registry publication.

`module.R4MF` controls build inputs, imports, target and image scope. The
Distribution image planner discovers manifests instead of maintaining a
second module list.
