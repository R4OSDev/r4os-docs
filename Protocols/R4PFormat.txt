R4P protocol format
===================

A current `.R4P` file is an R4M0 container whose manifest kind is `R4P`.
Older flat or dedicated R4P headers are historical and are not production
loader formats.

A protocol project declares in `module.R4MF`:

- module name and version;
- source language and entry source;
- exported protocol role and category;
- role dependencies;
- image target and `IMAGE_SCOPE`.

The module exports the protocol entry required by the Contract and imports
only the platform groups or other roles it needs. Disk discovery validates
the header, table ranges and R4P metadata, then registers the role as
`loaded`; it does not read sections or relocations. The first actual role use
loads and validates the complete image, resolves dependencies in manifest
order and initializes the module before dispatch. Missing, blocked, cyclic
and invalid candidates remain visible through the protocol status.

Protocols required before the task runtime use an explicit preload owner.
The USB HID-report, HID-boot, mass-storage BOT and SCSI-block protocols are
the current boot preloads; their installed disk copies do not start a second
module instance. Merely listing an unused disk role or reading its protocol
status does not load its image.

Platform group imports resolve to built-in Kernel providers and create no
file dependency. Other protocol roles remain normal module dependencies.

The formal R4M0, R4P metadata and R4MF v2 definitions are in
`Repositories/Contract/`. SDK build support is in `Repositories/SDK/`.
The current installed target root is `C:\R4OS\PROTOCOLS\`.

Explicit generation2 profiles select ProtocolInit2:2 and R4DEV:Query2:2.
The loader supplies the separate120-byte ProtocolApi2/PPI2 table from the
same protocol owner; ProtocolShutdown/Query/Dispatch remain shared exports.
Exactly one Init/Init2 with its corresponding export revision is accepted.
The original ProtocolInit:1 path and existing consumers remain unchanged.
See Contract/ABI/R4DDriver.txt and Docs/API/Generation2.txt for the canonical
technical boundary and the independently recorded native qualifications.

Protocol allocator (0.78.33)
---------------------------
ProtocolApi.alloc obtains the requested byte count and alignment from the
Kernel heap. ProtocolApi.free returns that same pointer and original byte
count to heap.free; it is not a deferred or module-lifetime allocation.
Null pointers and zero-length frees are inert. The heap retains its normal
pointer, exact-size and double-free validation. The API table and ABI version
are unchanged; existing R4P consumers use the corrected Kernel provider.
