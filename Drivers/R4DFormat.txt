R4D driver format
=================

A current `.R4D` file is an R4M0 container whose manifest kind is `R4D`.
The historical `R4D0` header is no longer a valid production format.

Required contract
-----------------

- `module.R4MF` version 2 with `KIND=R4D`.
- R4M0 module kind `r4d`.
- Export `DriverInit:1`.
- Export `DriverShutdown:1`.
- Import of the built-in R4DEV driver interface required by the
  implementation; no R4DEV file is loaded for this dependency.
- A target below `C:\R4OS\DRIVERS\` for distributed drivers.

The formal R4M0 and R4MF layouts are owned by `Repositories/Contract/`.
Driver API types and helpers are exposed by `Repositories/SDK/`.
The technical DriverApi v20 DMA, deadline-work and StorageBackend v2 lifetime contract is
canonical in `Repositories/Contract/ABI/R4DDriver.txt`.

Lifecycle
---------

Discovery validates and registers the container but does not necessarily
activate hardware. Activation calls `DriverInit`; unload first performs
class-specific preflight, then `DriverShutdown`, owner cleanup and registry
transition. The mapped R4M0 image may remain resident for a later reload.

New Driver API fields are append-only. A driver must verify the advertised
table size/version before using optional functions.

DriverApi v20 adds a versioned audio-refill request with an absolute tick
deadline, a nonzero stable device key and a one-through-four-tick callback
budget. The kernel copies the request and executes it on a separate bounded
EDF lane. Audio callbacks perform exactly one bounded pass and retain at most
one queued successor per device; every completion is joined and released
before IRQ, DMA or module teardown. Normal IRQ/task Driver Work keeps its
existing fair FIFO.

An existing resident driver buffer can be pinned and mapped into a bounded
segment list under an inclusive DMA mask, boundary, length, alignment and
segment-count contract. Pins and mappings are generation- and owner-bound;
the mapping is synchronized and unmapped exactly once before its pin is
released. Legacy contiguous DMA allocation remains supported.

StorageBackend v2 appends nonblocking submit, advisory cancel and reset. A
zero submit result transfers the request and buffer until exactly one
completion or a successful quiescing reset. `queue_depth` is the hardware
in-flight limit; version-1 and null-submit descriptors use the synchronous
depth-one adapter. Flush is an exclusive ordered barrier, and unload is
vetoed until every request and callback is quiescent.
