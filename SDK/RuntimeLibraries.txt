Independent Runtime-R4L libraries
=================================

R4STD, R4IMG, R4FONT, R4GFX, R4NV, R4AMD, R4ACO, R4NAK, R4GL,
R4VK, R4VIDEO and R4ENC are independent Runtime-R4Ls under
`Repositories/Libraries/`. Each library unit owns:

```text
Contract/   schema and compatibility baseline
Bindings/   Zig, C and generated Rust clients
Source/     provider implementation
Tests/      contract, conformance and runtime tests
module.R4MF and build files
```

A consumer imports `<MODULE>:<TABLE>:<MINIMUM_REVISION>`. The generic loader
resolves module and export names case-insensitively and supplies the provider
pointer in R4XStart. The library binding validates identity, API major,
revision, table size and required slots.

SDK71/Contract44 generate all local Rust records and typed clients from the
same LibraryContract.json and unchanged baseline. BINDING_RUST declares the
source; Bindings/Rust/Cargo.toml owns its independent consumer crate version.
The caller selects local package paths and component roots. Provider module
versions and interface revisions do not become Cargo project pins.

Rust clients borrow the exact App/provider loan. Unsafe calls retain the
local operation's ownership, blocking, threading and reentrancy contract.
Optional admission permits an explicitly missing import; malformed loaded
tables fail. C has corresponding *_init_optional functions. Query helpers
read the standalone library descriptor, separate from named API tables.
Higher language helper facades and Rust provider implementations are separate
qualifications. Current scope and evidence: LanguageParity.txt.

Compatible implementation changes and append-only table revisions remain
inside the library repository. They do not require a Kernel, central Contract
or core SDK change. Consumers change only when they use new slots or move to
an incompatible API major.

Loaded code remains valid for its lifetime. An update publishes a new
artifact atomically for a safe activation point; it does not replace code
beneath active function pointers.


Eigene Rust-/C-Implementierungsprojekte seit SDK0.64.85 (0.86.66)
---------------------------------------------------------------
C und Rust koennen echte R4L-Quellwurzeln mit lokalem Contract/Baseline und
regulaeren Query-/Tabellenexporten bauen. Ein unbenutztes IMPLEMENTATION_ZIG
ist nicht erforderlich; Zig nutzt es weiter als Implementierungsmodul.
Rust verwendet r4os-rust-r4l-v1 im gemeinsamen Build-RustModule.ps1 und den
passenden Host-Contractgenerator im Werkzeugpaket. BINDING_RUST ist dabei
der erzeugte Tabellenvertrag, keine zweite Implementierung. Der normale
R4M0-/Loader-/Consumervertrag und Contract44 bleiben unveraendert.

Caller besitzt Allokator, Session und Callbackzustand bis zur echten
Freigabe-/Stillstandsquittung. Ein fehlschlagendes Release behaelt die
Ressource. Der R4X-globale SDK-Allocator ist fuer gemeinsame Rust-R4Ls
abgewiesen. Keine Rust-&mut-Leihe ueber Callbacks halten. Vorlagen liegen
beim SDK unter Templates/R4L/C und Rust; Contract/Baseline und alle
Projektionen werden vor dem Bau mit dem Originalgenerator materialisiert.
Echter KVM4-Beleg, Source-/Artefaktpins und Grenzen: SDK/LanguageParity.txt
und Matrix r4l_providers_current_66. Neue Treiber-/Protokollrollen folgen
separat. Keine Windows-/Hardwarefreigabe aus vorbereiteten Binaerdateien.
