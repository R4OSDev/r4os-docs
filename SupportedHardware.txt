R4OS supported hardware
=======================

Primary target
--------------

The primary and continuously reproducible target is x86_64 QEMU using the
profiles from `Repositories/Distribution/QEMU/`. The standard module build
targets AVX2-class processors. The kernel itself is built without SIMD.

Current hardware classes
------------------------

- Boot/display: Limine and a linear framebuffer. DISPBLIT.R4D accelerates the
  bounded XRGB32 CPU copy through the canonical present contract; no native
  display-controller modeset, pageflip or GPU command backend is claimed yet.
- Storage: AHCI, NVMe, ATA PIO and USB mass storage paths exist. DOS/MBR and
  GPT partition discovery is supported on 512-byte logical sectors; GPT
  recognizes EFI System and Microsoft Basic Data partitions and can recover
  through the backup table. NTFS is the system-volume format; FAT32 remains
  available for boot and additional media.
- Input: PS/2 and USB HID keyboard/mouse paths.
- Timers: periodic PIT is the boot and degraded fallback. A free-running HPET
  supplies the modern logical tick; HPET legacy comparator 0 or a calibrated
  LAPIC supplies periodic active delivery and one-shot idle deadlines when the
  required ACPI/IOAPIC capabilities validate.
- CPU: x86_64 ACPI/LAPIC SMP with one BSP and up to 31 APs. INIT/SIPI startup,
  per-CPU architectural state and partial-AP failure fallback are covered on
  QEMU; one-CPU operation remains fully supported. CPU hotplug is not claimed.
- Network: RTL8139, RTL8168/RTL8111 and modern virtio-net drivers.
- Audio: AC97 and class-based High Definition Audio (HDA) output drivers
  plus MIDI, OPL3 and SID modules.
- USB: xHCI host controller and HID/mass-storage protocols.

The current xHCI backend initializes only the first controller found in PCI
order. Additional xHCI controllers remain uninitialized; attached keyboards
and storage on those controllers are unavailable. The inventory currently
repeats the global xHCI host status for every xHCI PCI function, so an
"active" inventory record does not prove that a particular controller was
initialized. This limitation also applies to Recovery 0.1.20.

Recovery input (0.76.5)
----------------------

Recovery uses the same PS/2 and USB HID keyboard paths and R4OS keyboard
layouts. Its HID admission excludes mice, including later topology changes;
the normal R4OS defaults remain unchanged. Hiding USB storage during a local
Recovery boot does not hide USB keyboards or disable their host controller.
The automated input acceptance covers QEMU PS/2 and USB keyboard models,
USB/local boots and BIOS/UEFI with four CPUs. USB-only cases disable i8042.
This does not establish compatibility with every physical USB keyboard.

Real hardware
-------------

R4OS has been booted from USB on real hardware, including a Lenovo IdeaPad
L340-15API with a Realtek RTL8168-family adapter. This is evidence for that
specific path, not a general compatibility promise. Firmware, ACPI, PCI
routing, storage controllers and display setup vary widely between machines.
Always keep a recoverable copy of important media.

The same Lenovo system has also completed an internal-drive boot through
Limine and AHCI.R4D 0.2.1 from a KINGSTON SUV400S37120G SATA SSD. Its NTFS
system partition mounted as `C:` while the separate Intel NVMe remained
available as an additional GPT device. The live acceptance observed two
preload-owned block devices, no built-in storage fallback, a successful
Device Manager storage selftest, RTL8168 DHCP and an SSH session.

The Lenovo audio path is documented in `Drivers/HdaStreamContract.txt` and
`Drivers/HdaHardwareAcceptance07110.txt`. HDA.R4D 0.3.13 enumerated both AMD
functions `1002:15DE` and `1022:15E3`, selected the latter with Realtek
`10EC:0257`, and passed cold/warm starts, internal-speaker playback, volume
and mute. Analog headphones remain untested. HDA support is selected by
PCI class 04/03 and is not limited to Intel controllers.

Images
------

Prepare installation media with the release's `CreateUSB.bat` on Windows
or `sudo sh CreateUSB.sh` on Linux. Both use PowerShell 7 and the original
release ZIP. Besides writing the GPT image, they place the original ZIP in
the Recovery installation cache and size DATA for the destination medium.
A raw copy of `disk.img` alone does not add that ZIP. See
`Deployment/USB-Erstellung.txt` for the supported workflow.

Security warning
----------------

R4OS is not hardened. Network services may use the standard credentials
`r4os` / `rosebud`. Never expose SSH, FTP, RDP or other R4OS service ports to
the public Internet or an untrusted network.
