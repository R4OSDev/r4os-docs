App-Projektstruktur 0.51.21
===========================

Ziel
----

0.51.21 migriert die Diagnostics auf die eigenstaendige SDK-Projektstruktur.
Diagnostics sind keine normalen Anwenderprogramme, sondern Contract-,
ABI- und Runtime-Waechter. Gerade deshalb sollen sie nicht als versteckte
Sonderfaelle im zentralen Build bleiben.

---------------------

- AudioDiag -> AUDIOD.R4X
- BootCoreDiag -> BOOTDIAG.R4X
- CleanupDiag -> CLEANUPD.R4X
- ClipboardDiag -> CLIPD.R4X
- CStartSmoke -> CSTARTD.R4X
- DisplayDiag -> DISPLAYD.R4X
- FsDiag -> FSDIAG.R4X
- HardwareDiag -> HWDIAG.R4X
- InputDiag -> INPUTD.R4X
- LoaderDiag -> LOADERD.R4X
- LogServiceDiag -> LOGDIAG.R4X
- MemorySuite -> MEMSUITE.R4X
- NetDiag -> NETDIAG.R4X
- NetR4pDiag -> NETR4P.R4X
- NetSvcDiag -> NETSVC.R4X

- R4XStartSmoke -> R4XSTARTD.R4X

Alle Projekte besitzen seit 0.51.21:

    build.zig
    build.zig.zon
    src/
    module.R4MF
    README.txt

Der lokale Projektbuild erzeugt das Artefakt im jeweiligen `zig-out/`. Der
zentrale `Code/build.zig`-Build bleibt fuer das Standardimage erhalten, muss
aber dieselben fachlichen R4L-Imports tragen wie die Projektmanifeste.


Zielpfad
--------

Diagnostics bleiben im Image unter:

    C:\R4OS\SOFTWARE\TERMINAL\DIAG\

Das ist bewusst derselbe Runtime-Pfad wie vorher. Geaendert wird die
Build- und Contract-Sicht, nicht der Aufrufpfad im System.


Imports
-------

Jedes Diagnostic-Manifest nennt `IMPORT=R4SYS:Query:1`, weil R4XStart-
Programme den Basisstartvertrag darueber erhalten.

Fachliche Imports sind sichtbar:

- AudioDiag: `R4AUDIO`
- BootCoreDiag, CleanupDiag, FsDiag, HardwareDiag, LoaderDiag, MemorySuite,
  StorageDiag und UsbDiag: `R4DEV`
- ClipboardDiag: `R4DESK`
- DisplayDiag: `R4DEV`, `R4DRAW`
- InputDiag: `R4DESK`, `R4DRAW`
- NetDiag, NetR4pDiag und NetSvcDiag: `R4NET`
- R4CfgDiag und StdDiag: `R4STD`
- SynthDiag: `R4AUDIO`, `R4DEV`

R4CFGD importiert R4STD:Query:1. Es gibt keinen produktiven R4CFG-Import und
keinen Legacy-Alias fuer diese Stufe.


Sonderfaelle
------------

`CSTARTD.R4X` ist das C-Diagnostic. Es nutzt `sdk.addR4XStartC`, die
gemeinsamen C-Header, den C-Startup und das R4OS-Linkprofil.

`SVCAPPD.R4X` ist eine Service-Class-Diagnostic. Das Projekt nutzt
`sdk.addR4XService`, bleibt aber unter dem Diagnostic-Zielpfad. Das
`module.R4MF` verweist auf die TestInjection-Service-Konfiguration, weil
SVCAPPD dort als Testdienst mit `/HOLD /ENDPOINT` gestartet wird.


Abnahme
-------

Projektbuilds:

    powershell -NoProfile -ExecutionPolicy Bypass -File Tests\Gate\Run-DiagnosticProjectBuilds05121.ps1

Statischer Strukturcheck:

    DevTools\Zig\zig.exe run Tests\Gate\CheckDiagnosticProjectStructure05121.zig

Standard-Smoke:

    DevTools\Scripts\Build.bat -test

Der Strukturcheck prueft lokale SDK-Bindung, Buildprofil, Manifeste,
R4L-Imports, Diagnostic-Metadaten, SVCAPPD-Servicebezug, die Doku-Anker und
den Ausschluss alter R4CFG-Imports.
