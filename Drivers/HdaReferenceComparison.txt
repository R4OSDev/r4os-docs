HDA reference comparison for R4OS
=================================

Reference set
-------------
The reproducible, SHA-256-checked source archive is local at
ExFiles/Reference/Hardware/HDA/. Download-References.ps1 verifies 20 files:
Intel HDA 1.0a, Intel HDA033-A and HDA043-A, QEMU commit
a4bb4b10c9d43d416f6e8bc9bb5c8f372fd80769, and Linux stable commit
2609d60e2f6d0b8a96563baa08b56482962cebaa. These files are development
references and are not shipped in R4OS images.

Root causes
-----------
R4BASIC and r4os.subsystem_runtime originally submitted 480 frames, or 1,920
bytes, every 10 ms. The previous HDA driver placed each packet in a 4,096-byte BDLE and
zeroed the remaining 2,176 bytes. At stereo S16 that is exactly 544 unwanted
zero frames after 480 useful frames. BEEP.R4X happened to write 1,024-frame
blocks and therefore concealed the general defect; R4BASIC never routed its
BEEP statement through BEEP.R4X.

After fixing that packet/period mismatch, the R4BASIC gorilla.bas capture
still sounded noisy and contained short fragments. The stream descriptor used
0x0021. Intel HDA and the pinned QEMU source define bits 6:4 value 2 as 20-bit,
while R4OS DMA buffers contain signed 16-bit samples. The corrected descriptor
value is 0x0011: 48-kHz base, bits 6:4 value 1 for 16-bit, and channels-minus-
one value 1 for stereo. The exact QEMU anchors are
QEMU-a4bb4b10/hw-audio-intel-hda-defs.h and
QEMU-a4bb4b10/hw-audio-hda-codec.c in the local reference archive.

The remaining four-vCPU TCG gaps had two independent causes. First,
PeriodBook could leave its producer behind an LPIB consumer jump, so new PCM
waited a complete ring traversal. The producer now realigns directly after
the current hardware period and a complete unobserved 640-ms window forces a
stopped descriptor reset. Second, synchronous 10-ms AUDSVC writes were too
expensive to refill QEMU's host-paced HDA model. Kernel and service now
preserve service_api_result_busy, the SDK retries without consuming caller
PCM, and R4BASIC sends 960-frame 24-kHz S16 packets which HDA linearly expands
to four 48-kHz hardware periods. Four packets are submitted once for startup;
steady playback submits one packet per 40-ms deadline and never polls capacity
in every host cycle. HDA starts at 20 ms and bounds the running reserve at
320 ms. Application Close and driver shutdown drain requested frames plus
three explicit postroll periods before the bounded descriptor reset.

Validation
----------
- stream_ring.zig host tests cover wrapped byte queues, the two-period normal
  and one-period drain start thresholds, producer ownership, missing periods,
  recovery and cyclic wraparound.
- AudioDiag pattern tests cover nonzero samples and phase preservation across
  packet boundaries; long-mode pacing follows the published HDA fill level.
- Analyze-QemuWav.ps1 selftests reject injected 480/544, sample-loss and
  internal-silence fixtures.
- Standard-QEMU short capture: 8,280 input frames, continuous signal,
  Known480_544Patterns=0, all path error counters zero.
- Standard-QEMU long run: 2,880,000 frames, 6,000 writes, all path error and
  silence counters zero. Long-mode feeding follows HDA fill level so QEMU
  guest-clock drift is not misreported as a hardware-ring underrun.
- The 20 August gorilla.bas four-vCPU TCG capture no longer contains the
  characteristic 160/320-ms stale replay. With the retained 320-ms running
  reserve its first six eighth notes are complete; later TCG stalls still add
  silence and therefore remain a QEMU listening limitation rather than a
  physical-HDA acceptance.

Open hardware row
-----------------
The Lenovo IdeaPad L340-15API still needs a cold-boot record with PCI codec,
MSI/INTx route, LPIB behavior, five-minute tone, repeated start/stop/close,
BEEP.R4X and R4BASIC BEEP/PLAY. Until that run exists, QEMU evidence must not
be described as a physical HDA acceptance.
