R4OS connectivity architecture
================================

The normal data path is:

```text
R4D network driver -> kernel net core -> R4P protocol roles
                   -> R4X network services -> R4NET SDK facade
```

RTL8139, RTL8168 and virtio-net drivers publish adapters through the common
driver interface. Ethernet, ARP, IPv4, ICMP, UDP, TCP, DHCP and DNS roles are
loadable modules. DHCPSVC, DNSSVC, TCPSVC and UDPSVC own long-running service
state and expose bounded endpoints to applications.

Receive work has one bounded context boundary. An external NIC interrupt
acknowledges and classifies its device cause, then publishes the exact adapter
through DriverApi v23. The event-driven BSP `net-rx` task moves the device
cursor and copies frames into Netcore's fixed 64-slot queue. Serialized
protocol processing dispatches at most 32 frames per activation, using the
optional `net-rx-ap` worker when registered callbacks permit AP execution and
the BSP worker otherwise. Polling and maintenance remain on the BSP task.
TX-, link- and configuration-only causes do not execute the RX stack.
A full common queue leaves the current device entry
owned by the driver for an event-driven retry. The 10-ms all-adapter poll is a
watchdog for missing IRQ routing, not the normal intake clock.

Queue ownership and latency stay observable: accepted frames equal processed,
transition-cancelled and currently occupied slots. NETRX additionally reports
high-water, backpressure, batch-budget ends, IRQ/event/fallback wakes and the
schedule-plus-handoff latency tail.

NetBackend v2 appends an explicit offer for queue count, buffer ownership,
scatter, checksums, VLAN/segmentation, interrupt moderation, notification
suppression and asynchronous completion. DriverApi v24 returns the immutable
selection after registration. Unknown and rejected optional bits keep the
mandatory canonical flat frame byte-identical; rejected required bits reject
the backend. The current BSP implementation selects one RX/TX queue and only
the VirtioNet RX TCP/UDP checksum-valid capability. IPv4 remains verified in
software, as do all RTL8139/RTL8168 frames and every unselected metadata path.
NETCAP verifies capable/incapable and unknown fallback rules; NETRX and driver
status expose selected, used, software-fallback and malformed-metadata counts.

QEMU user networking and host forwarding are host profiles, not assumptions
inside guest services. Real hardware receives addresses and routes through
the same R4NET/service path.

Timeout, backpressure, close, abort and stale-handle outcomes remain explicit.
A service reactor must not block on a complete session; worker ownership and
completion carry longer operations.

Kernel TCP writes are bounded by the peer-advertised window and by a bounded
catalog of unacknowledged segments. A write may therefore report a partial
byte count or zero (would block); TCPSVC and callers retain the unsent suffix.
Cumulative ACKs retire every covered segment, while partial ACKs retain only
the unacknowledged suffix for retransmission. Retransmit state is bound to the
connection ID, physical slot and slot generation, and all RTO and TIME_WAIT
deadlines use the monotonic kernel tick domain. Waiting for incoming data does
not arm or retransmit outgoing payload.

ARP resolution in RX workers (0.89.59)
--------------------------------------
Kernel 0.1.460 treats an expired next-hop ARP entry as deferred work in both
RX task incarnations: the BSP net-rx poll/maintenance task and the optional
net-rx-ap protocol worker. Task ID and generation identify the current worker;
a foreign task or a reused ID keeps the ordinary bounded resolver behavior.
The existing serialized protocol consumer must return to its outer frame
queue before it can consume an ARP reply. Waiting synchronously while sending
a TCP ACK can otherwise stall that same queue after the 30-second cache TTL.

On a cache miss, an RX worker requests ARP at most once per adapter per 500 ms
and returns Busy immediately. Existing TCP ownership retains an unsent ACK,
FIN or retransmission for a later activation. Init and ARP flush clear the
pacing deadlines. The short network owner protects only resident metadata;
the request callback runs after release. Public R4NET records, the cache TTL,
and bounded three-attempt resolution for ordinary callers stay unchanged.

Core/KernelArp08959.json records the regular-kernel routed transfer comparison,
source-derived host cases and existing NETWORK LIMIT acceptance. The recovery
kernel has its independent correction in Recovery 0.1.68. STANDARD covers the
five general workloads and provides no network-throughput measurement.

TCP readiness ownership (0.84.28)
---------------------------------
TCP waits use separate resident queues for establishment, readable and closed
conditions of one connection, and accept/data conditions of one listener.
A connection ticket contains its exact slot, ID and native generation; a
listener ticket contains slot, port and a non-reused lifetime generation.
Waiters keep that ticket across the whole operation. Closing/reopening the
same port cannot adopt a stale accept or let its late cleanup close the new
listener. Incoming connections retain the listener generation that admitted
them, so a new listener cannot accept an old unclaimed connection.

The existing waitable TCP task owner captures copied readiness at release.
Runtime admission then publishes the atomics and matching wakes together.
Scheduler predicates read only that projection and never acquire the TCP
owner. No table pointer or TCP/runtime owner spans sleep. Only positive
readiness and exact identity retirement signal the corresponding condition
queues; unchanged ACK traffic does not broadcast to unrelated connections.
Readable waiters also recheck a changed terminal state, while the original
read predicate, read results, 250-ms fallback slices and deadlines remain.

R4NET tables and fixed public records stay unchanged. tcp_sig in the native
trace now counts actually woken tasks, previously received segment broadcasts;
those values are not directly comparable. Existing NETWORK LIMIT adds one
bounded native wait group inside its TCP performance-contract category, with
real queues and eleven exactly retired own tasks. Original TCP/IPC listener
restart checks are bundled. STANDARD has no TCP-specific workload.
Implementation, acceptance and limits: Core/KernelTcpWake08428.json.

TCP burst and ACK policy
------------------------

A TCPSVC write carries at most 4,068 payload bytes inside the unchanged
4,096-byte IPC message. The kernel treats that request as one measurable
write and emits as many wire segments as the negotiated peer MSS permits.
R4OS advertises an Ethernet MSS of 1,460 bytes; when the peer sends no MSS
option, the conservative IPv4 fallback is 536 bytes. A burst stops exactly
at the first remote-window, retransmit-catalog or backend limit and reports
confirmed partial progress. Each connection owns 48 retransmittable slots,
covering 70,080 payload bytes at the local MSS and therefore a complete
unscaled TCP receive window without the former eight-segment ceiling.

Window scaling is optional and bilateral. R4OS offers scale 2, accepts at
most the RFC limit 14 and never scales the window field in SYN or SYN-ACK.
Peers without the option continue with the unscaled window contract.

In-order receive data may defer its ACK for at most 40 ms. A second segment,
FIN, duplicate/out-of-order data, missing sequence progress or a full receive
buffer requests an immediate ACK. Outgoing payload may satisfy a pending ACK
by piggybacking it. Reads emit a separate ACK only when they expose a material
receive-window update. The event-driven net-rx task flushes deadlines; its
10-ms wake remains a safety watchdog. Explicit service/SDK adapter polling is
skipped while that task owns IRQ and watchdog progress and is retained only
as the pre-task fallback.

R4NET's optional `tcp_performance` snapshot and the existing TCPSVC/NETIOD
status paths expose write calls and bytes, wire segments, current and peak
outstanding ownership, window/catalog/backend stalls, pure/delayed/immediate/
coalesced/piggybacked ACKs, polls, retransmits and negotiated options. Hot
writes update O(1) counters; full snapshots are read only by diagnostics or a
status request.

The source-derived 0.75.17 baseline had three separate kernel writes for a
4,068-byte service request (1,460 + 1,460 + 1,148), eight retransmit slots or
11,680 service-payload bytes before an ACK, an immediate ACK for every data
segment plus a possible read-side ACK, and readiness polling before normal
service/SDK writes. In 0.75.18 the same request is one kernel burst with three
segments at MSS 1,460, 48 slots, delayed/coalesced ACKs and optimistic writes
that poll only after actual backpressure. No historical runtime-throughput
number is claimed because the old path had no equivalent counters and this
roadmap permits only the short SMP4 smoke, not a separate long network run.


Adapter ownership and driver teardown (0.78.56)
---------------------------------------------
Netcore assigns each registration a positive reference that is not reused
during the boot. External drivers return this unchanged for RX, work scheduling
and capability queries; it is separate from compact enumeration indices.
Removing an earlier adapter no longer changes a surviving driver's reference.
The R4D bridge resolves references under callback admission, and registration/
removal drains those lookups. Removed references are rejected even after reuse
of the backend slot. RTL8168 needs no artifact or cold-bind change.

VIRTNET 0.1.4 closes callback admission and waits for device-status zero after
reset, with at most 1000 one-tick waits. A missing confirmation or failed IRQ
removal retains DMA and makes shutdown fail; owner cleanup then preserves the
existing module/resources. Failed initialization uses the same teardown.
Reference: VIRTIO 1.2 sections 3.3.1 and 4.1.4.3.2:
https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html
RTL8139 0.1.4 keeps timed-out TX slots and bytes until hardware completion or
confirmed reset. Timeout is reported once per pending slot in tx_errors, while
transmit returns busy without rotating or overwriting the live descriptor.
This deliberately does not promise recovery of a permanently stalled device.


DHCP lease and request states (0.78.57)
-------------------------------------
NETDHCP 0.1.2 and Kernel 0.1.126 use the existing DhcpOp.client_ip to distinguish
SELECTING from requests for a bound lease. SELECTING uses ciaddr=0 and options
50/54. Renew sends from the current address to the original server, with the
matching Ethernet next hop; rebind sends to broadcast. Both put the current
address into ciaddr and omit options 50/54. The existing route/ARP resolver now
also accepts the selected DHCP adapter. A renew wait ends by T2, a rebind wait
by expiry; the earlier caller deadline is retained.

0xffffffff explicitly means an infinite lease: expiry and automatic renew/
rebind are disabled and remaining values retain the sentinel. A manual renew
remains possible. Finite T2 uses u64 multiplication. Invalid T1/T2 ordering
falls back to half and seven-eighths of the lease. One-/two-second leases keep
their exact expiry with automatic T1/T2 disabled, because two positive whole-
second deadlines cannot fit; a zero-duration or addressless ACK is rejected.

A successful ACK replaces router/DNS with its supplied values. Missing
options mean no gateway and no configured resolver; the server ID is never a
substitute. A failed renewal retains the last confirmed complete lease unless
a NAK invalidates it. There is no implicit carryover from an offer or old ACK.

DHCPSVC 0.1.5 obtains the kernel-computed elapsed/remaining values through the
existing structured kernel IPC response. Its restart changes neither the
lease age nor its remaining time. No raw status or service ABI grows.
Lease age currently starts at the kernel's ACK/bind point; it is no longer
derived from service observation time.

References: RFC 2131 sections 3.3/4.4.5 and table 5, RFC 2132 sections 3.5/3.8:
https://www.rfc-editor.org/rfc/rfc2131.html
https://www.rfc-editor.org/rfc/rfc2132.html

Family-aware provider foundation (0.90.31)
----------------------------------------
Contract86 / SDK174 add copied family/address/endpoint/deadline records and
versioned RPCs on the existing DNS/TCP/UDP service endpoints. The new Query2
clients have separate explicit socket lifetime and complete resolver pages.
Provider INFO probes the actual backend; an older kernel advertises no new
TCP/UDP capability. Existing IPv4 operations and imports remain available.
The original TCP owner retains exact FIN/reset cause for these new sockets;
the original UDP FIFO reports consumed datagram length and truncation.
There is no second transport registry or kernel IPv6 stack. AAAA codec support
alone grants no IPv6 transport/resolver capability. The first provider is
IPv4-only, without typed Listen/Accept, implicit mapping or family fallback.
Normative contract: Contract/API/NetworkFamily.txt. Provider boundaries,
scope and qualification evidence: API/NetworkFamily.txt.


External IPv6 foundation (0.90.32)
---------------------------------
Contract87 / SDK175 / Kernel470 add external NETIPV6, NETICMP6 and NETNDP
owners over the original NIC/Ethernet path. VIRTNET advertises multicast only
after a real ALLMULTI control acknowledgement. Interface work binds the real
nonreused NIC link epoch, provider and clock; missing multicast or entropy
reports zero capability. Link-local DAD, manual addresses, /64 SLAAC and
bounded ND/reassembly operate in the controlled peer qualification. Fixed
1280-byte TX does not claim PMTU discovery. A duplicate link-local remains
unusable until a real link epoch reset. TCP/UDP/DNS IPv6 endpoint, AAAA,
dual-stack and mapped capability stay false until0.90.33. Existing IPv4 paths
and application imports stay available. Normative limits:
Contract/API/Ipv6Providers.txt; actual qualification and retained failed
attempts: API/NetworkFamily.txt. Physical NIC/IRQ/DMA and Windows are separate.
