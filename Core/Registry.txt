R4OS registry and configuration
================================

The system registry stores operating-system and shell state in the R4R1 hive
`C:\R4OS\REGISTRY\SYSTEM.R4R`. R4SYS owns the runtime read/write API and
the SDK exposes a typed registry facade. Applications must not edit the hive
as an ordinary file.

Registry paths begin with `SYSTEM`. Values are typed strings, integers,
booleans or binary data. Reads return borrowed data only for the duration
defined by the API. R4SYS keeps the complete validated view bound to its R4R1
generation. Repeated reads of that generation search resident bytes and do
not allocate, reload or revalidate the file. A short state lock protects only
the resident view; no Registry lock spans file I/O, waits or heap activity.

Mutations are serialized separately, build the next generation into an
inactive fixed slot and keep readers on the previous complete generation
while TMP is written and verified. The filesystem's atomic ownership transfer
publishes TMP as SYSTEM.R4R and retains the previous object as SYSTEM.BAK.
Only a verified durable target switches the resident view; a definite failure
leaves the old generation visible, while an ambiguous completion is retried
before another read or write may proceed. Selected noncritical UI traces may
be deferred, but shutdown flushes them before final storage flush.

Large enumerations use the optional generation-keyed snapshot contract.
`registry_snapshot_begin` captures the hive generation, the flat key-table
index and the exact child-key or value range. Each `registry_snapshot_page`
then advances directly within that range; it never rescans entries before the
cursor. A page contains at most 32 caller-owned entries and at most 16384
caller-owned data bytes. A value that does not fit still advances the cursor
with its full length and an explicit data-omitted flag. If the active
generation changes, the page returns `restart` with zero rows. Callers must
discard every prior page from that attempt; an incomplete or restarted
snapshot is never a truncated success.

`registry_batch_mutate` accepts at most 32 offset-based Set/Delete operations
whose paths, names and payloads live in one caller-owned blob of at most 16384
bytes. R4SYS validates the complete batch, builds exactly one inactive
candidate, commits it once and publishes one generation. Duplicate targets,
invalid payloads, capacity failures, missing delete targets and commit errors
leave the previous visible generation unchanged and never expose a partial
batch. The older single-value operations and their ABI slots remain valid.

R4S files are separate schema-oriented text configuration files. They are
used for services, associations, desktop, input, time, updates and
component-local settings. R4STD owns the reusable R4S/config parsing and
atomic write helpers; the registry is not a universal replacement for these
files.

The binary R4R1 layout is summarized in `RegistryFormat.txt`. The public
registry operations and result codes are generated from the platform
Contract.

Registry mutation cost and REG (0.78.27)
---------------------------------------
REG SET/DELETE now send only the requested value operation through the typed
Registry facade. They do not read, rebuild or replace SYSTEM.R4R as a normal
file. The shared transaction gate therefore includes other writers and
previously acknowledged resident writeback values. A failed or missing
mutation reports failure. Explicit whole-hive text import remains a separate
file-based operation and needs its own future transaction work.

The shared builder uses a bounded name index for runtime-size key/value sets,
links children once in insertion order and groups values once with the
mutation owner's index workspace. Duplicate validation also uses a bounded
index and still compares actual case-insensitive names on collisions. The
binary layout, stable within-key order, generation and full validation are
preserved. Larger generic capacities keep the existing no-allocation fallback;
old builder callers may omit the additional value-order workspace.

A source-instrumented host fixture with 512 values under one key measured
262655 versus 1807 name comparisons for build plus validation, with identical
22693-byte output. A mixed tree measured 33222 versus 1397 comparisons with
identical 30256-byte output. These are comparison counts, not guest latency
or a filesystem throughput claim.


Konfigurationsspeicherung ab 0.78.63
-----------------------------------
R4STD0.2.2 behandelt nur R4SYS-Read -3 als fehlende Datei. Null Bytes
bezeichnen einen vorhandenen leeren Bestand. Zu grosse Dateien ergeben
config_error_buffer_too_small (-3); sonstige Lesefehler werden als neuer
config_error_read_failed (-9) gemeldet. Die bestehenden Fehlernummern und
Tabellenlayouts bleiben gleich; der Library-Contract wurde ausschliesslich
um diese Fehlerkonstante erweitert und kontrolliert neu generiert.

Einzelwerte werden erst nach erfolgreicher TMP-/BAK-Wiederherstellung aus
dem tatsaechlichen Zielinhalt komponiert. Unveraenderte Schluessel bleiben
erhalten. Nicht lesbare oder ungeeignete Zieldaten und nicht lesbare
Sicherungen stoppen den Vorgang vor Loeschen oder Schreiben. Ein gueltiges
TMP hat bei fehlendem Ziel Vorrang; sonst kann eine lesbare BAK verwendet
werden. Fehlgeschlagenes Umbenennen einer brauchbaren Sicherung behaelt sie.
Scheitern Publikation und Rueckbenennung, liefert saveDocument
error_recovery_failed; TMP und BAK bleiben fuer die Wiederherstellung stehen.
Es gibt keine bedingungslose Aussage, dass ein Rueckbau abgeschlossen sei.
Der Zig-Pfadvergleich ruft den kanonischen SDK-Helfer equalsIgnoreCase auf.

Nachweis: bestehender R4STD-Build mit47 Hosttests einschliesslich zweier
gebuendelter Fehler-/Wiederherstellungsfaelle und instanziiertem Binding-
Pfadvergleich; fuenf gezielte Hostfaelle fuer die betroffenen Oberflaechen und
REG; ein SMP4-Gastlauf mit privaten TMP/BAK-Daten, erhaltenem Fremdschluessel,
geaendertem COUNT, unveraenderter4097-Byte-Datei nach Groessenfehler und
vorhandener leerer Datei. Kein neuer kanonischer Testlauf angelegt.

REG-Lesestatus ab 0.78.63
-----------------------
Nur -3 gilt als fehlender Hive. Leere, zu grosse und anderweitig nicht
lesbare Dateien bleiben als vorhandener ungueltiger Bestand erkennbar.
Die sichtbare Leseausgabe unterscheidet diese Fehler. SET/DELETE verwenden
bereits seit0.78.27 die gemeinsame Registry-API; dieser transaktionale
Schreibpfad bleibt unveraendert. Selbsttests folgen gesondert in0.78.64.


Registry-Selbsttests ab 0.78.64
-----------------------------
REG WRITESELFTEST/APITEST/MIGRATESELFTEST und RegEdit /SELFTEST sind nur fuer
ein ausdruecklich privates Testimage vorgesehen. Die Test-Injection liefert
TEMP/REGTEST.R4S mit R4OS_REGISTRY_SELFTEST=PRIVATE_IMAGE; Slim/Full enthalten
diese Testdeklaration nicht. Das ist eine Diagnosekonvention und kein Rechte-
modell. Ohne Deklaration brechen die schreibenden Tests vor Mutationen ab.
REG SELFTEST bleibt ein reiner Speichertest.

Der gemeinsame SDK-Helfer registry_selftest laesst keine bereits vorhandenen
TMP/BAK-, Original-, Restore- oder Displaced-Dateien als eigenen Bestand zu.
Lesefehler werden nicht als Abwesenheit behandelt. Die Originalsicherung wird
vollstaendig mit dem zuvor gelesenen Inhalt verglichen. Zum Rueckbau entsteht
aus ihr eine gepruefte zweite Stagedatei; nur diese wird durch R4SYS atomar
uebernommen. Erst nach erfolgreichem Ersatz, Bytevergleich und Bereinigung
werden REGSYS.SAV beziehungsweise SYSTEM.REB entfernt und OK ausgegeben.
Fehler behalten die Originalkopie; ein erneuter Test ueberschreibt sie nicht.
REGs temporaere Exportdatei wird ebenfalls nur bei vorheriger Abwesenheit
verwendet. Die acht schon zuvor auf16Byte ausgerichteten Scratch-Slices
bleiben bis zur Freigabe ausgerichtet und werden jetzt rueckwaerts freigegeben.

Begleitkorrektur in Kernel0.1.128: Externer atomarer Dateiersatz invalidiert
betroffene Registry-Cacheansichten auch nach einem moeglicherweise partiellen
I/O-Fehler. Der interne Registry-Commit benutzt denselben Dateipfad mit
explizit internem Abschluss, damit sein eigener Kandidat erhalten bleibt.
So stimmen nach einem Restore Dateibytes und gelesene Cachegeneration wieder
ueberein. Kein neuer ABI-Slot und keine neue Kernel-Diagnoseschnittstelle.

Nachweis: vier gebuendelte Hostfaelle fuer fehlgeschlagene Kopie/Publikation,
bestehende Sicherungen, fehlend/leere Hive, beide App-Abschluesse und alle
acht teilweisen Scratchallokationen. Ein lokaler SMP4-Gast verwendet eine
frisch erzeugte private246-Byte-Hive, prueft beide vorhandenen Selbsttests,
Originalbytes, Cachegeneration1 und Bereinigung. Keine regulaere Installation
wird als Testbestand verwendet. Belege unter Temp/roadmap-078-execution/07864.
