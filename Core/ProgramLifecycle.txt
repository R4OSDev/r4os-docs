R4OS program lifecycle
======================

Identity and storage
--------------------

Programs, tasks and threads are stable heap objects addressed by an ID and a
generation. Registries use reusable tombstone slots and chunked storage;
removing one object does not move another live object or its locks.
Numeric stress counts are test baselines, never capacity declarations.

Lifecycle
---------

A program is admitted, receives its R4M0 image and payload ownership, resolves
imports, creates its root task and enters R4XStart. Normal exit, requested
close, kill and failure all converge on ordered cleanup. Handles remain
generation-checked so stale observers cannot operate on a reused slot.

Kernel 0.1.238 also preserves an admitted GUI module's unique
`app.role=desktop_host` declaration in ProgramInstanceInfo.flags (mask 0x08).
This immutable owner marker lets an ordinarily spawned replacement Desktop
bind WindowService without becoming a boot shell. It grants no permissions
and changes neither launch role, scheduling nor boot readiness. Missing or
other declarations leave the bit clear; duplicate declarations reject the
module metadata. Console launches never receive the GUI owner marker.
Such a Desktop host starts without waiting for another Desktop to attach
it as an application window. Ordinary handle-based GUI launches retain
their two-step attach transaction. Desktop claims WindowService ownership
before creating display/capture owners; concurrent replacement is rejected
until the previous process generation has actually retired.

Ein optional instrumentierter R4Basic-Start behaelt seine R4SUBSYS1-ID von
Explorer-Probe beziehungsweise Headless-Aufnahme ueber Desktop-Hostrequest,
Kernel-Admission, R4M0-Ladeende und R4XStart bis zum ersten gastgetriebenen
Frame. Der Kernel wertet die Argumentrecords ausschliesslich passiv fuer
begrenzte serielle Diagnose aus; Admission, Besitz, Scheduling und der
oeffentliche R4XStart-Vertrag bleiben davon unveraendert. Loader-Deltas werden
vor und nach genau diesem Startfenster aufgenommen und nicht aus seit Boot
kumulierten Absolutwerten als Appkosten ausgegeben.

Der vom Bootlauncher gestartete Shellprozess besitzt zusaetzlich genau bis
zu seinem ersten nutzbaren Frame oder Prompt den optionalen R4SYS-
Readinessmarker. Der Marker ist an die konkrete Shellinstanz gebunden und
idempotent. Ein Exit vor diesem Marker beendet die Bootmessung als Fehler;
spaetere oder normale Programmstarts koennen einen abgeschlossenen
Bootmessstand nicht veraendern.

Die erfolgreiche Aufnahme des Shelltasks beendet den einmaligen
`kernel-main`-Boottask endgueltig; sein Descriptor wird ueber den normalen
deferred Reap entfernt und nimmt nicht weiter an der Schedulerrotation teil.
Davon getrennt friert erst der Readinessmarker das Bootmessfenster ein und
uebergibt Bootrenderer sowie Ausgabesink an die Benutzersitzung.

Solange der Bootrenderer aktiv ist, veroeffentlicht der interne Shelllauncher
vor jeder Admission-Grenze einen kurzen Detailmarker. Er unterscheidet
Pfadauflosung, Header/Image/Stack, Registry- und Completion-Reservierung,
Instanz/Task/Thread-Publikation, Ready-Aufnahme, Shelltask-Pin und den Aufruf
von `R4XStart`. Bleibt der letzte Marker bei `R4XStart aufrufen`, hat der
Bootshelltask den Benutzercode erreicht, aber noch kein `boot_ready` gemeldet.
Diese Diagnose aendert weder den R4XStart-Vertrag noch die Lebensdauer- oder
Schedulinggrenzen.

Hard kill and reaping may continue only when the target holds no tracked lock
and has no unwind guard. Owner resources are detached before their backing
payload is freed. Program, task and thread registries are not locked across
I/O, wait, yield, callback or resource destruction.

The Task ownership registry is separate from the scheduler's Ready, timed-wait
and deferred-reap projections. A state transition updates all affected links
within one scheduler-runtime owner boundary; a successful yield no longer scans unrelated
registry objects for deferred destruction. ProgramThread and asynchronous-I/O
owners bind an immutable, generation-checked execution context before their
blocked Task is published Ready. Current R4X ownership is therefore resolved
directly. ProgramThread storage remains alive until the exact Task generation
has been released. Asynchronous I/O binds a permanent pool-worker object;
its current request retains the submitting ProgramThread identity, process
generation and stream owner. The worker detaches this request before exposing
completion, so Close can recycle it without retiring a Task or stack.

The existing 64 asynchronous request slots are served by at most eight BSP
workers, four for files/streams and four for service replies. Each lane scans
pending slots round-robin and sleeps on events when empty. Queue residence
counts against finite service timeouts. Normal completion retains the worker;
hard cancellation stops only the exact worker handling that request and
replaces it after retirement. The cancellation claim excludes pickup of a
different request until that retirement is confirmed. Queued requests cancel
without creating a Task. The resident worker-stack ceiling is 512 KB instead
of 4 MB for 64 simultaneous request Tasks; the unchanged completion table
also bounds completed requests whose callers have not yet closed them.

Die Ready-Publikation eines neu aufgebauten R4X-Tasks erfolgt
erst nach dem vollstaendigen Registry-Commit und weckt danach den ausgewaehlten
Prozessor per Reschedule-Anforderung. Das ist keine normale WaitQueue-Wake und
veraendert weder Waitresultat noch Programmvertrag; es verhindert lediglich,
dass ein bereits im Idle angehaltener AP neue Arbeit erst am naechsten
periodischen Tick entdeckt.

A naturally returned ProgramThread transfers its Task storage to the scheduler
reaper through `exitCurrentAndRetire`. It remains the owner of its kernel exit
epilogue until it has released its execution pin and that scheduler reaper has
removed the exact Task generation. Publishing the instance as retired may wake
the program reaper, but that reaper neither kills nor claims an `exited` thread
while either owner is still present. Only after the terminal context switch
and independent Task release may ProgramThread, I/O and program payload
teardown continue. A hard-killed thread remains program-reaper-owned and is
not covered by this wait. This separation prevents two reapers from competing
for the terminal Task transition, stranding the last instance pin or releasing
the exit stack before foreground completion can be published.

The fixed stream-slot table publishes a small generation-checked owner and
volume projection under the program-state owner. ProgramThread and
process cleanup first consult that projection. An owner without stream leases
needs no filesystem gate; otherwise each actually occupied volume lane is
acquired independently and only as an immediate attempt. A busy relevant lane
defers retirement without parking the reaper, while unrelated volume work can
never delay an owner that has no stream on that volume. The same projection
serializes fixed-slot reservation across concurrent streams on different
volumes.

Blocking process completion waits (0.82.27)
------------------------------------------
Kernel 0.1.239 parks a blocking program_handle_wait caller for one tick
between generation-checked completion reads. A zero timeout still returns
immediately; finite and unlimited waits retain their existing result contract.
No registry lock, completion-node pointer or new lifetime lease spans sleep.
Each wake revalidates the handle, including concurrent completion consumption.

The old yield-only loop could continuously hand off the program registry
mutex between BSP/AP callers and send reschedule IPIs. A CPU-only OssiPC
reproduction timed out both four-second waits before its BSP child reached
the 100-ms sleep, with over 514,000 mutex contentions. The same two immutable
test programs pass with the corrected kernel in SMP4: the waits complete in
about 103/110 ms. This CPU result does not itself prove GPU reset or WSI
reconstruction. No additional recurring test group is introduced.

Console wait and retained output
--------------------------------

Since 0.78.8, a generation-checked program Close request publishes its flag
under the registry owner, releases that owner, and signals both console
input and desktop activity. This lets timer-free hosted GUI event loops
observe Close immediately even when the program has no console payload.

Since 0.69.67 a console owner may combine the nonblocking bulk read with the
optional generation-bound R4DESK input wait. Queue state, generation and wait
enrollment form one handoff: producers publish bytes before waking, and close
requests wake an otherwise idle Terminal so it can observe lifecycle state.
The one-byte poll remains a compatibility path and is not required for an
event-driven host.

Kernel 0.1.263 retains a console input target lease in its exact stable
ProgramThread, including inherited console targets. Short unwind guards
protect lease construction and normal release; no guard spans input sleep.
After hard kill detaches the exact scheduler Task and its intrusive waiter,
thread retirement releases the retained target before thread/stack teardown.
Normal return clears the same lease once under the program registry owner;
failed identity or release retains it for retry. A stack-local defer alone
cannot own a lease across a killable wait: DESKTOP's hard close previously
left a dead terminal's extra pin behind, preventing completion and window
removal. SPECTRA CHECK LIFECYCLE /CONSOLEWAIT isolates real parked Close, Kill and redirected
child Kill cases from the existing lifecycle profile and checks its exact
resource/registry baseline. It adds no recurring gate.

Console producers store normalized bytes once in sealed 16-KB backing blocks.
The private completion transcript and an inherited visible transcript retain
references to the same blocks, with independent ordered segments and 16-KB
drop boundaries. Blocks cannot be overwritten while either view references
them. Normal exit converts private references to completion ownership;
completion reads stay stable until the generation-checked handle is reaped.
Output revisions and Desktop activity are published per complete write batch,
not per byte.

The 0.69.67 guest acceptance kept two idle Terminal windows at a combined
runtime-tick delta of zero across twelve Desktop frames. PAUSE, buffered
follow-up input and requested close completed with three input-wait blocks and
three wakes; the active phase produced 15 bounded view revisions and 15
Desktop signals. A text-heavy child retained 4,704 byte-exact completion
bytes from 96 writes while the private and visible views shared their backing
data; those writes produced 192 view revisions and 96 Desktop signals.

Stack sizing and telemetry
--------------------------

R4X address reservation is fixed at admission; physical stack commitment is
not. The memory profile selects reserve and initial commit, with optional
memory.stack.reserve and memory.stack.commit metadata overrides. Stack faults
grow the committed span downward, normally by 64 KB and far enough to cover
a deeper fault in the same reservation. A moving 4-KB guard precedes that span;
the final 4 KB of the reservation remain unavailable. There is no automatic
extension of the reserved address range. Growth also requires physical budget
and a context without an already-held no-sleep/runtime owner.

The entry trampoline switches stacks before R4XStart, including SDK startup.
Loader work before that switch still uses the caller's stack. Direct kernel
API calls and imported library calls keep the program execution stack; they
do not switch to the separate 64-KB kernel-task stack. Secondary R4X threads
receive their own growing program stack; a zero reserve argument inherits
the profile reserve. Kernel and driver workers use their fixed resident
64-KB Task stacks with 16-KB guards. An unresolved stack fault reaches the
common fatal CPU-exception path, rather than a recoverable program-start error.

Only detail builds (-Dmetrics=true) fill fresh, cached and critical-reserve
kernel-task stacks and newly committed R4X stack spans with a canary pattern.
Normal return and common release then scan the untouched prefix once and
record high-water and TSC create/release cycles. Base builds retain functional
guards, stack growth, creation/release counts and R4X size aggregates without
canary scans or measured high-water. See Diagnostics/KernelInstrumentation.txt.
The instrumented R4BASIC acceptance emits bounded `[R4XSTACK]` serial records
that tie its root or secondary thread to owner, module, profile, reserve,
initial and final commit. Profile and scheduler-role aggregates use atomic
updates on SMP; ordinary programs do not add serial traffic. Teardown remains
idempotent and no registry or scheduler lock is held while memory is released.
Virtual-range IDs are monotonic for one boot. If a stack-range release crossed
its destructive boundary but lost the acknowledgement, a later `NotFound`
therefore completes that exact retirement instead of requeueing a stale stack
forever; all other release failures remain retryable and retain their owner.

Historical sizing in a one-CPU Test guest measured maxima of 139,256 bytes for
normal, 241,344 for desktop, 48,560 for service, 202,456 for large-service and
176,232 for build-tool program stacks. The normal/service/desktop reserve is
therefore 4 MiB; large-service/build-tool use 8 MiB. Initial commits remain
64 KiB for normal and service and 128 KiB for desktop, large-service and
build-tool. Tiny remains 2 MiB/64 KiB. Browser and workstation remain
32 MiB/256 KiB until a representative Klickifax-specific run exists. Every
profile continues to grow committed stack in guarded 64-KiB steps.

Kernel-task high-water reached 39,800 of 65,536 bytes. The committed 64-KiB
kernel stack therefore remains unchanged, also preserving the earlier real
net-rx evidence that 32 KiB overflowed. The eight-entry reclaimable stack
cache and four critical-reserve stacks likewise remain unchanged; their hit,
miss and occupancy counters are included in the teardown evidence.

SMP placement
-------------

Since0.85.13, optional R4SYS v26 functions expose exact-generation Thread
CPU sets, desired CPUs and bounded work classes. Ordinary foreground/shell
main tasks, global-console and unaudited owners retain CPU0-only admission. Audited
background instances declare runtime.parallel=owned-v1; their child threads
inherit that immutable module approval. Public sets cannot expand it.
A shell-hosted application with a private console can use this background
role; visible console output alone does not identify a legacy foreground
start. The explicit programRun path creates role0; its main remains BSP-only.
Since0.85.18 separately declared, explicitly created compute descendants may
use APs without changing that main or console owner (see the worker section).
API contract and pending/save semantics: API/ThreadPlacement.txt.

Initial/wake placement and bounded queue transfer share the0.85.11 topology
chooser. Since0.85.12 exact Running-plus-Ready load gap>=2 permits populated
targets; urgent empty refill is independent of one periodic checkpoint per
CPU quantum. One donor and eight rotating candidates bound each attempt.
Forced diagnostic/launch bindings, dedicated driver/asynchronous-I/O owners,
live locks, permit handoffs, preemption and incomplete retirement stay guarded.
Both exact physical currents remain protected even when logically Ready.

A public request for a physical current remains pending until its real saved
switch. The outgoing continuation is temporarily private under Runtime
admission. Existing assembly publishes its full RSP and installs the incoming
stack before r4os_finish_context_switch applies policy and republishes Ready
work. The owner is unlocked only afterwards. CPU0 has a resident initialized
idle continuation, with FPU state, so a sole local current can leave too.
Saved blocked waits keep their precise task-owned wait/timeout nodes.

Ready age, generations, saved FPU/RSP and exact task-bound unwind counters
survive rehome; class changes share the remaining preferred-role budget of
that activation. No CPU reservation, hotplug or realtime guarantee follows.
Evidence: Core/KernelBalance08512.txt/.json and
Core/ThreadPlacement08513.txt/.json; current audited owners remain in
Parallelitaet.txt.

AP admission since 0.78.50 follows detected -> starting -> parked ->
qualified -> online. Only the BSP can confirm a parked CPU after its clock
registration completes. The shared release does not replace that per-CPU
confirmation. Lifecycle transitions and their scheduler mask publication
use the narrow scheduler runtime owner; CPU initialization, clock sampling,
LAPIC operations and bounded waits remain outside it.

A startup or activation rejection is terminal. A late AP stops before
scheduler entry if its starting/qualified transition was rejected. An online
publication that wins at the timeout boundary remains admitted; the BSP
cannot subsequently mark it as a failed startup. Online/failed diagnostic
counts come from the confirmed states, and timeout reports are recorded once.
Clock status exposes prepared samples only for qualified/online/stopping
CPUs, so a late sample cannot restore a rejected CPU's visible registration.
Stopping removes scheduler eligibility before the stop IPI; offline is also
terminal. The fixed CPU-local layout and public ABI stay unchanged.

Logical exit and physical switch-out are separate states. `running_cpu`
keeps an exiting or remotely woken Task unreapable until assembly has saved
its outgoing RSP. Normal exit, close, kill and failure still converge on the
same generation-checked teardown, and failed/offline CPUs are never selected
for new work.

Inventory
---------

R4SYS exposes paged, restartable program/task/thread inventory. A generation
change requests a restart and requires the caller to discard partial pages.
R4DEV exposes diagnostic summaries. Fixed-layout compatibility structures
are never extended in place; new telemetry uses append-only versions.

0.76.8: Storage ownership during retirement
-------------------------------------------
Process and thread retirement first drain asynchronous I/O and stream slots,
then release persistent volume uses and hand abandoned exclusive operations
to the storage cleanup worker. A claim prevents payload retirement until its
I/O is drained and remount has finished or failed visibly. Owners without
claims do not acquire the topology gate. NTFS mount inspection and cache
invalidation retain references to the large metadata cache instead of copying
it onto a 64-KiB kernel-worker stack.

VM release completion and failed admission (0.78.31)
---------------------------------------------------
Image release returns completion explicitly. A failed cleanup retains the
image range identity and mutable stack progress in the stable instance;
retirement cannot advance to slot reuse or READY on a partial VM release.
The final VM owner step reports errors and confirms that every remaining
range of the instance has been released, including image kinds.

An unpublished admission can also own ranges before image/stack fields are
bound to its instance. Cancellation therefore retains its create-state slot,
generation and unattached completion until all owner ranges finish. Payloads
are detached once and saved stack progress survives each attempt. Failure
hands that same slot to the existing program-reaper queue as cancel_pending;
no new worker or separate allocation is required. The reaper retries outside
the program registry lock, then clears the slot and frees its completion once.
Duplicate cancellation cannot compete with the queue or worker owner.
Successful admission cancellation does not publish a process completion.


Working directory (0.78.67)
---------------------------
CWD is the calling process's canonical drive and directory, exposed through
the existing env_get/env_set functions. It is not stored a second time in
the environment block. env_set("CWD", value) requires an absolute drive path,
normalizes separators and dot segments, rejects embedded NUL, and confirms
that the target exists as a directory before publishing the process context.
Invalid, unavailable, non-directory or overlong targets leave the old context
intact. env_get returns the full drive-qualified path; a short output buffer
is unchanged. No public function, table layout or result constant is added.

Path snapshots and publication use the program-state owner. Filesystem work
runs before that owner is acquired; child admission copies the parent's
complete context. Only launches without a parent use the bootstrap drive's
initial directory. Terminal inherits CWD at startup and changes its prompt
only after env_set confirms a CD or drive switch. It does not rewrite CWD
when synchronizing ordinary environment values. Relative file operations,
redirection and child launches therefore share one context; a child's later
change remains private. CD C:relative uses the current C directory. Switching
to a different drive still selects its root. VOL without an operand uses
the confirmed current drive.

A short SMP4 guest checks same-named private files, TYPE/COPY/REN/DEL/MD/RD,
redirection, direct child and nested Terminal inheritance, failed directory
and drive changes, short CWD reads and VOL on two local volumes. R4OS and
Recovery carry the same correction; no broad shell or filesystem profile.

Grafikpuffer seit 0.79.5
-----------------------
Gemeinsame Raster und R4DRAW-BOs verwenden denselben residenten Speicher-
und Lease-Besitzer. CPU-Maps, Exporte, Jobs und Scanout koennen eine
Produzenteninstanz ueberleben. Neue Imports enden mit dem Produzenten;
Seiten und Budgets werden erst nach erfolgreichem Rueckbau freigegeben.
Details, graphics-VM-Fenster und Abnahmen: Drivers/GrafikPuffer07905.txt.
Ab 0.79.35 haelt der gemeinsame GPU-VA-Broker Bereichs-/Bindungsauftraege und
BO-Leihreferenzen ueber Caller-Schluss und Kill hinaus. Vor Exit-Publikation
schliesst der Programm-Besitzer unter dem BO-Owner die Annahme. Seit 0.83.1
haelt er dabei eine genaue Registry-Generation gepinnt, ohne den Registry-Lock
zu halten: BO-Rang 100 darf nicht unter Registry-Rang 110 erworben werden.
Nach erneutem Sperren gewinnt weiterhin nur der erste Exit; ein Unwind-Token
schuetzt die temporaere Leihe auch gegen Kill des Callers. Leihe und Kontext
bleiben bis zum Ende der Exit-Benachrichtigungen erhalten. Aufwendiger
Abbau bleibt ausserhalb der Registry. Anlageergebnis und physischer Abbau
haben getrennte residente Ereignisse. Exaktes Task-Retirement loest Waiter;
Elternabbau wartet auf bestaetigten Kindabbau. Details: GrafikVulkan07935.txt
im Verzeichnis Drivers; dort auch die Grenze zum modellierten Treiberbeleg.


Kernel 0.1.154 bindet die Grafikidentitaet vor Init an den echten R4D-Start,
bei fruehen Treibern vor Task-/SMP-Beginn. Normaler Work nutzt BOs ohne
Lifecycle-Guard. Close sperrt neue Zugriffe und erlaubt bestehende Freigaben;
Cleanup prueft die Retention nach Work-Quieszenz erneut. Lebende oder unklare

Resident calls under owner locks (0.79.5)
----------------------------------------
Direct R4X API calls retain the program execution stack. The first no-sleep
or runtime owner admission prepares 64 KB of resident stack headroom; growth
under an already-held owner is forbidden. Program/thread stack reservation,
moving guards, canary telemetry and ordinary release ownership remain the
same. The added ProgramStorage case exercises both owners at the real guard.
Details and the reproduced AVL corruption: Core/Speicherverwaltung.txt.

Graphics waits and hard kill (0.79.6)
------------------------------------
Asynchronous R4DRAW fences have explicit task-ID/generation wait records.
They do not keep an UnwindToken across the wait: hard kill must be able to
detach the task and its intrusive Event node. releaseProgramTaskGeneration
then retires that exact graphics waiter reference. Program exit closes all
producer queues; physical device work and consumer references survive until
the authenticated R4D reports quiescence. BO backing never belongs to a
waiting task's stack or to its destructors. See Drivers/GrafikQueues07906.txt.

R4D CPU heap ownership (0.79.10)
-------------------------------
The actual R4D start epoch now also binds resident CPU heap allocations. This
ownership is independent of the task that issued allocate: work callbacks use
the authenticated driver context and do not borrow an R4X ProgramInstance.
Split allocation/publication and release/completion enroll a task unwind token
under the runtime owner. No payload operation or backing free spans that owner.

Closing refuses new allocations, while existing handles can still be released.
After DriverShutdown and all backend/IRQ/work/DMA users have quiesced, generic
cleanup frees leftovers and retires the empty CPU owner. In-flight operations
or failed backing release veto unload and preserve the closed epoch. This does
not add an RM callback scheduler, mutex contract or device completion guarantee.

Dedicated R4D tasks (0.79.10)
----------------------------
DriverApi32 adds a generic scheduler service for driver-owned callbacks,
independent of shared serial Driver Work. Exact owner/start epoch, Task ID and
generation bind before Ready publication, with guarded stack, full module
FPU state and an initial unwind lifetime guard. BSP placement is the default;
parallel execution is explicit and grants no program identity or legacy I/O
admission. CPU heap ownership resolves the real dedicated execution context.

Cooperative stop wakes only thread-service sleep/join waits. A join lease
retains its target through timeout or caller cancellation; self join fails.
Callback completion is distinct from exact Task/stack retirement. Parent
shutdown closes starts and must quiesce callbacks before generic resources
are destroyed. Failed creation/free and outstanding waits remain represented;
closed driver/module ownership cannot retire early. Details and byte layouts
are in Contract/ABI/R4DDriver.txt and Drivers/GrafikFirmware07910.txt.

R4D semaphore waits (0.79.10)
----------------------------
DriverApi33 exposes real resident counting semaphores through the existing
scheduler WaitQueue/FIFO handoff. Each blocking acquire retains its exact
record and a Task unwind token until return. Owner close refuses creation,
but existing operations remain usable; neither owner close nor dedicated
thread stop cancels semaphore waits or manufactures a permit. An outer finite
join can fail without claiming the callback has stopped. Drivers complete
shutdown by their real protocol, otherwise the closed module stays retained.

Try and one-permit release are resident IRQ-capable operations; allocation,
free and nonzero waits require an admitted sleep-capable task. Generic cleanup
runs after actual IRQ/work/task quiescence and before DMA/CPU heap release.
A counter has no Task holder ownership, so the driver must stop all users
before explicit destruction; the kernel also rejects retained acquire leases.
The byte and error contracts are in Contract/ABI/R4DDriver.txt.

Earlier AP deadlines and BSP idle (0.79.10)
------------------------------------------
The timed-wait projection is global and its hardware deadline source belongs
to the BSP. blockCurrent compares the old minimum with the new finite wait
under the runtime owner. If an AP publishes an earlier deadline, it sends
the existing reschedule IPI to CPU0. The BSP's existing atomic idle check and
STI/HLT sequence consume that notification and recheck the current minimum.
This also covers an idle source that was disarmed with no prior deadline.
APs never program the BSP-owned HPET/LAPIC timer. No extra timeout scanner or
periodic polling is introduced. The same explicit SMP4 semaphore contention
probe exercises this path while its init caller waits in a finite join.

Dedizierte R4D-Tasks: expliziter Selbstabbruch (0.79.10)
----------------------------------------------------
Ein Treiber kann fuer einen nativen Aufruf Startflag 2 aktivieren und die
optionale DriverThreadApi80-Funktion abort_current nutzen. Nur der aktuelle
authentifizierte Task darf mit negativem Ergebnis an seinen noch aktiven
Kernel-Aufrufrahmen zurueckkehren. IRQ, gehaltene Kernel-Locks, Runtime-
Sektionen, aktive Waits und mehr als der initiale Unwind-Guard verhindern
den Transfer. Niemand kann einen fremden Task abbrechen.
Der bestehende threadMain-Abschluss publiziert Ergebnis und Statusflag 4,
weckt Joiner und gibt den initialen Guard zuletzt auf. Taskgeneration,
Stack und Record werden weiterhin erst nach positivem Ruhen freigegeben.
Der Transfer fuehrt keine Modul-Defers oder fremde Unwind-Handler aus:
Speicher, eigene Locks, Semaphoren und DMA bleiben Verpflichtung des
nativen Besitzers. Erst Peer-Quieszenz erlaubt dessen Ressourcenabbau;
unklare Ausfuehrung oder GPU-Aktivitaet erfordert weiterhin Retention.

Dedizierte Treiber-Taskbindung und wartender Status (0.79.10)
-----------------------------------------------------------
Kernel0.1.146 ergaenzt current_request bei Offset80 der optionalen
DriverThreadApi, Version 1/88 Bytes. 72..79 Byte Kapazitaet erhalten 72,
80..87 erhalten 80, ab 88 werden 88 Bytes geschrieben; fremde Randbytes
bleiben unangetastet. Die Funktion liefert nach Pruefung des tatsaechlich
laufenden dedizierten Tasks und Treiberbesitzers ausschliesslich dessen
unveraenderte Startanfrage (Handler, Kontext, Erzeugungsflags). Ein gueltiger
32-Byte-Ausgabepraefix wird vor einer Kontext-/Besitzerablehnung geleert;
ein ungueltiger bleibt unveraendert. Keine Allokation, Warteoperation oder
zusaetzlicher Unwind-Guard. Caller-Kontexte bleiben bis zur Taskfreigabe
resident; die Kernelbindung uebernimmt deren fachlichen Inhalt nicht.

Statusflag 8 stammt ausschliesslich vom real blockierten Task in seiner
eigenen Treiber-Sleepqueue unter dem Runtime-Owner. Es wird nicht durch
eine vorangestellte Callback-Bereitschaftsmeldung ersetzt und beschreibt
keine beliebigen anderen Waits. Sobald der Task wieder lauffaehig ist,
ist dieses Flag nicht mehr gesetzt. Flag 4 und 8 werden als Startflags
abgewiesen. Native Aufrufdaten und Fristen besitzt weiterhin der Treiber;
der normale Taskabschluss, Peer-Quieszenz und die Freigabeverpflichtungen
werden durch eine Frist nicht aufgehoben.

Graphics during system transition (0.79.10)
-----------------------------------------
Kernel 0.1.151 drains display execution before acquiring a driver owner.
Output/firmware writers remain closed while DriverShutdown may restore and
release the held display. The terminal R4D path includes display and network
drivers, retains DMA/module memory, and rejects quarantined or failed owners.
For graphics it closes new resources, jobs and dedicated callbacks; confirmed
hardware shutdown must leave no display, GPU-memory or queue ownership and
no active dedicated callback. Shared Work is then cancelled/drained. Any
unproven handoff enters poweroff or halt instead of warm reset. This grants
no generic cleanup permit and does not weaken ordinary unload admission.
See Drivers/GrafikFirmware07910.txt and its system_transition_checkpoint.

Kernel 0.1.259 includes audio drivers in the terminal warm-reset pass. An
empty HDMI output can still own running DMA, so absence of application
streams is not quiescence. The existing prepare/begin/commit owner cleanup
closes audio callback admission, invokes DriverShutdown and verifies full
backend/IRQ/work/DMA cleanup before acknowledging the audio owner. Failure
retains or quarantines ownership and vetoes warm reset. Audio is stopped
before the earlier-initialized display driver is dismantled; storage remains
available for the terminal reboot log. Ordinary unload uses the same barrier.

Kernel 0.1.152 / DriverApi35 lets the exact live dedicated Task post normal
Work with flags=0 and its current owner epoch. Stop or parent close rejects
new submissions; an already admitted enqueue stays retained by its Task.
Shutdown must stop/join the pacing Task and drain its completion before
resource cleanup. The dedicated caller gains no direct MMIO/DMA admission.
See the Contract repository's ABI/R4DDriver.txt for the unchanged table and
the existing normal FIFO, owner binding and terminal display requirements.

Process-owned notifications and native library workers (0.79.35)
---------------------------------------------------------------
R4SYS v19 appends notification_create/query/notify/wait/close. The kernel owns
resident records and Task wait nodes; userland owns mutex/condition policy.
Read the revision before checking the caller predicate. Wait compares and
enrolls under the scheduler runtime owner, so notify cannot be lost between
those steps. Handles never repeat within a boot and resolve only in the
calling process. Close drains waiters before freeing; a failed free retains
the closed identity for retry. No caller pointer or unwind token spans sleep.
Hard kill detaches the actual Task node. After exact retirement of all process
threads, the reaper must release every record before reusing ProgramInstance.
Kernel 0.1.183 also accepts thread entrypoints in executable sections of the
program's imported R4L slot/generation bindings. Data, unrelated modules and
stale generations remain invalid. Existing image-relative entries keep their
normalization; library entries must be absolute. Code pinning lasts through
thread retirement, as it already does for preemption in imported R4L code.
Details and bounded evidence: Drivers/GrafikVulkan07935.txt/.json.

R4SYS v20 adds program_local_get/publish for process-owned runtime contexts.
Nonzero keys publish one immutable, nonzero value until exact process
retirement. Get reports zero for absence; Publish returns the existing winner
when another thread published first. Errors leave the output untouched. The
kernel owns only resident association records in ProgramRuntimePayload;
userland owns and initializes the pointed-to data before publication. No
user callback, allocation or payload access occurs under the runtime owner.
Losing records whose free fails remain attached for reaper retry. Records
are removed after all process threads retire and before VM teardown. A
shared R4L may use its pinned static key address, but must not store a caller's
context, allocator or AppBundle in shared library globals.

R4SYS v21 appends thread_current_handle. It copies the current ProgramThread
and ProgramInstance IDs and generations through the existing fixed-layout
ProgramJoinHandle, including for the main thread. Lookup uses the immutable
Task execution owner; it does not scan a registry, allocate, wait, pin or
create a join lease. The running Task retains its ProgramThread until exact
retirement. Errors leave output unchanged. The borrowed identity distinguishes
reused numeric IDs but does not extend lifetime or change join admission.
Libraries may key thread-local state by this identity; its storage, cleanup
and language-runtime policy remain in userland. The ordinary ThreadDiag path
checks create/current agreement, yield stability, wrong-generation rejection
and absence after join. It does not force numeric-ID exhaustion.

R4SYS v22 appends cpu_capacity without changing the v21 prefix. CpuCapacity
reports one atomic scheduler-admission mask count and the immutable SMP boot
plan's dense slot count, including failed/offline slots. Available capacity
excludes CPUs not admitted by scheduler/clock qualification. This global
advisory count does not describe a particular Thread placement set; query
thread_placement_get for that exact generation since0.85.13. The query allocates
nothing and leaves output unchanged on failure. Counts are advisory, not CPU
reservations, firmware totals, CPUID package counts or physical cache topology.
Mesa uses this userland-visible capacity to size work; renderer policy stays
outside the kernel.

R4SYS v23 appends program_exit at offset1240, preserving the v22 prefix.
An admitted call terminates the calling process from either its main thread
or a worker and does not return. Only natural and failed reasons are accepted;
invalid reason, missing program ownership or unsafe kernel execution context
return an error without initiating exit. Userland owns normal atexit/TLS/stdio
cleanup; this primitive runs no foreign callbacks or stack unwinding.
The first committed process exit wins. The caller uses the same pinned exit
epilogue and terminal scheduler handoff as thread_exit; its peers, I/O,
notifications, VM and graphics follow the existing process reaper. Ready
completion still follows actual cleanup. Ordinary secondary thread_exit stays
thread-local, and external program_handle_kill still rejects self-kill.

Terminal display cleanup tasks (Kernel 0.1.213, DriverApi36)
---------------------------------------------------------
Ordinary driver close/unload still closes new thread queries and starts.
During terminal system-transition shutdown only, the synchronous display
lifecycle owner may query/start a dedicated cleanup task after existing
tasks receive stop/wakeup. Calls from existing or cleanup child tasks do not
inherit that permission. Heap, resources, semaphores, GPU BOs and work
admissions remain closed; cleanup uses retained ownership and mappings.
After the shutdown callback, including failure, thread admission closes
before the existing callback/task/display/GPU quiescence checks. A retained
task or unacknowledged hardware state still vetoes warm reset and backing
release. This is a lifecycle semantic clarification; DriverApi36 remains
656 bytes and adds no further slot or public payload.

Mutex handoff ownership (0.81.14)
--------------------------------
A selected mutex waiter becomes the owner under the scheduler runtime owner
before its Ready transition. The exact task generation already has one held
lock count, so kill, killIdentity and retirement defer hard death even before
the lock caller resumes. The first retry only acknowledges the transfer; it
does not recurse. Earlier cancellation/timeout/kill removes the wait node.
After transfer the ordinary owner must resume, unwind and unlock; there is no
unowned selected-waiter interval requiring a wake-all fallback.

Stack failure diagnostics (0.84.1)
---------------------------------
Rust/program/stack_fault.rs retains the latest stack failure per CPU in
resident atomic fields. Recording uses the interrupted task's existing
generation-checked thread/async execution binding, without allocating,
waiting, scanning registries or reading stack contents. Main, secondary,
kernel-task and exception stacks remain distinct. Growth admits only the
current bound stack; a foreign reservation no longer supplies a fallback.

The record distinguishes terminal reserve exhaustion, the exact current
kernel guard, physical-budget rejection, failed VM commit/guard updates,
forbidden growth and missing resident page-in continuation headroom. CR2,
original RSP/error word, reserve/commit/guard bounds, task/process/thread
generations and the existing R4X image/tag are retained. Unknown associations
remain unavailable; a current R4X image is not attribution of a driver or
library RIP. Optional high-water estimates are separate from committed bytes.

Crash serial output and framebuffer show the same resident facts. Legacy
crash attribution no longer traverses task/thread lists or acquires the
physical owner for a MemoryBlock catalogue scan; general block attribution
stays unavailable. The serial mirror uses the COM1 route rather than the
console-only raw writer. R4DEV v14 appends only
stack_fault; Spectra METRICS STACKS exposes its text/JSON view and renders
unavailable identities/bounds as null. This is one latest record per CPU,
not an event history or persistence across reboot. Fatal exceptions still
halt; controlled R4X stack exhaustion is the later 0.84.4 step.
Scoped acceptance, artifact identities and limits: KernelStack0841.json.

Resident loader workspace (0.84.2)
---------------------------------
Program classification/loading and R4D/R4P metadata probes keep their two
4-KB read windows in a 9208-byte resident heap workspace. The R4L scan owns
its 36352-byte pending set through dependency resolution. Initialization
writes the final allocation directly; no large return-value/array copy is
placed on the caller stack. Cache policy and module memory budgets stay
with their existing owners.
Rust/memory/scratch.rs retains the exact task unwind token across all I/O.
Short RuntimeGuard scopes admit/release that token; no runtime or heap lock
spans the operation. Allocation failure returns the token and the existing
error form. Early returns close the workspace; release must receive the
heap acknowledgement before the token is returned. A failed release is a
terminal invariant failure and retains the pin. Temporary data owns no
external resources/destructors. The launch reader closes before child
publication/execution, so a foreground child never extends that lease.
Compiled frames, caller lifetimes and acceptance: KernelStack0842.json.

Independent foreground compute workers (0.85.18)
-----------------------------------------------
runtime.workers=owned-v1 preserves a separate immutable per-instance worker
declaration, independently of the main/background runtime.parallel policy.
The explicit compute creation flag admits a reviewed worker. A compute
caller passes that role to zero-flag descendants too; BSP/UP execution never
turns it into a console/GUI producer. Foreground/shell main tasks retain their
original BSP placement. Default main-created threads keep legacy semantics.
Console input/output, host claims, program launch and GUI production do not
transfer to the compute role. Exact generations, VM/FPU, joins and retirement
are unchanged. Existing ProgramInstance offsets/core budget remain intact.

An App.system context borrows the caller-owned Bundle on the R4XStart main
frame. Worker buffers alone are insufficient after an unconfirmed join:
the complete main/App/Bundle frame must remain live through terminal stop.
R4Pack requests process exit in that case and does not return or free its
in-flight context. Successful preparation joins every admitted worker before
serial canonical assembly. Close/Join and Kill/Reap keep their actual owner
acknowledgements. Core/ForegroundWorkers08518.txt/.json records evidence and
explicit untested pending-input/active-file-I/O failure limits.
